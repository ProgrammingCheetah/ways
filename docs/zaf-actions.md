An **action** is a runnable file that `zaf` names, lists and runs through `zaf do <name>`. Actions are how a project or a machine makes zaf its own, and zaf is the abstraction layer over them: it owns the names, the listing, the environment, the log, the modes, the phases and one exit contract; what a name *does* is the action behind it. zaf ships none: whoever sets zaf up writes them, and every place a verb shells out is a name the project or the machine must provide. What Claude assumed beyond the rulings is listed in §9, open to veto.

## 1. Principles

1. **Make it yours.** A project or a machine decides what a name does by putting a file of that name in its actions folder. zaf ships no actions and has no last word on a step that shells out.
2. **zaf is an abstraction over actions.** A verb is a stable name and a composition of named steps; each step resolves to an action the project or the machine provides. `zaf do push` is the project's `push`, or the machine's, and so is every verb that pushes.
3. **Two tiers, resolved by name.** The project's `.zaf/actions/`, then the machine's `~/.zaf/actions/`. The first file found wins; `zaf do` lists every name with its tier. `zaf do` on a name no tier provides is `NOT_RUN`, exit 125 (§5); a verb's step with no action is exit 2 (§4).
4. **Composable.** An action's body may call `zaf do <other>` and any verb: `zaf do something` may be `zaf do something_1; zaf do something_2`. Each call gets its own log; an outer log names the inner ones.
5. **One contract.** Exit 0 is success, non-zero is failure, 1 the canonical one; every non-zero code an action can return is declared in its metadata with its meaning. Code 125 is reserved for zaf: `NOT_RUN`, the body never ran. What zaf prints on a failure leads with a word, `FAIL` or `NOT_RUN`, because a model reads words; a pass prints nothing. Nothing else is promised about an action's output: the log holds it.
6. **Metadata and body.** Every action file has two parts: the metadata, which names it to zaf (description, exit meanings, mode, group, phases, limits), and the body, which runs. A file without metadata is not an action.
7. **Every action has a mode.** Callable by anybody by default, not every action by everybody: a mode like a file's (§3), three digits for the Engineer, the action's group of roles and every other role, bits for seeing, overriding and running.
8. **Phases are the guard that holds.** An action names the Team Phases it may run in; zaf derives a task's phase from the board and its own records, never from the environment, and refuses the action outside them.
9. **State and logic stay in zaf; slices are action language.** The board's leases and labels, the ask ladder and quote check, the spawner's tick, the check engine, the brief, the transcript parser, doctor and setup stay verbs and are not overridable. The slice family is actions: `zaf do slice-open | slice-pr | slice-merge | slice-drop`, written by the project.

## 2. The two homes

**The project's `.zaf/`, committed.** Projects gain `.zaf/` as a folder of their own. The manifest is `.zaf.toml` at the project root, `.zaf/config.toml`, or both: when both exist they combine, and `.zaf.toml` wins on a property they both set. `ZAF.toml` is retired.

```
.zaf.toml                 the manifest at the root (optional; wins on conflicts)
.zaf/config.toml          the manifest inside the folder (optional; the two combine)
.zaf/actions/<name>       the project's actions, committed
.zaf/roles/               per-role project instructions pasted into briefs, committed
.zaf/.gitignore           written by zaf setup, never by hand: an allow-list, so actions and roles stay tracked
.zaf/local.toml           machine-private overrides (ignored)
.zaf/logs/                action logs (ignored)
.zaf/runs/ .zaf/profiles/ .zaf/workspaces/ .zaf/slices/ .zaf/spawn.state .zaf/spawn.lock .zaf/guard.json .zaf/asklog.jsonl   as today (ignored)
.zaf/ticks.jsonl .zaf/ticks.lock   the tick trace, a line per real tick for 14 days, and its lock (ignored; §5.1)
.zaf/scheduler.lock .zaf/tick.request   the running scheduler's lock, naming it, and the requests for a tick (ignored; §5.1)
```

**The machine's `~/.zaf/`, the global home.** Laid out like a project's `.zaf/`: `config.toml` (machine-wide defaults every project here inherits, below the project's own manifest) `actions/` (the machine's actions, seen by every instance on it) and `ledger.db` (zaf's record of what every run cost, §10). Its place is configurable (`ZAF_HOME`); the default is `~/.zaf/`. `zaf setup` creates it, with a commented `config.toml` and an empty `actions/`, and creates the project's `.zaf/` with its `.gitignore`; any verb that finds either missing runs that setup first, non-destructively, so the Engineer may call `zaf setup` from the beginning or let the first verb do it. A `ZAF.toml` still at the root is read as before, with a warning on stderr; only an explicit `zaf setup`, run by the Engineer, moves it to `.zaf.toml`, once, and says so.

**Precedence.** Manifest: `.zaf.toml` > `.zaf/config.toml` > `~/.zaf/config.toml` > the pack's defaults, property by property. Actions: project > machine; a project file shadowing a machine file can never widen its run bits (§3), and `zaf doctor` names every shadowing.

**No built-ins.** zaf itself ships no actions. The teams pack carries the standard set in its `actions/` folder, and `zaf setup` installs it once into the machine tier, `~/.zaf/actions/`, from the pack installed in the generated profiles: each file the machine tier lacks, with its mode, never over a file already there, so an action the Engineer edited is left byte for byte, and nothing is deleted. Every project on the machine inherits them, and a project keeps its own copy in `.zaf/actions/` only of what differs (the project's file wins, §1.3). `zaf doctor` lists the names the project's verbs and steps need (`gate` lines aside) and which tier provides each, and `zaf do --tier machine <name>` runs the machine's when the project's shadows it. The ways repo keeps its own set in its `.zaf/actions/` (§7), isolated from any other project's.

The zip test (framework §7.6) gains one named exception: `~/.zaf/` is the machine's zaf home, like its credentials. A project whose steps resolve to a machine action depends on that machine; `zaf doctor` reports each one, so the dependency is visible.

## 3. The file

Two parts. The **metadata** is the comment block that opens the file, right after the shebang when there is one: every line is the language's comment marker, then `zaf`, then a key, a colon and a value. The **body** is everything after the first line that is not metadata.

```sh
#!/bin/sh
# zaf description: merge the task's pull request and mark the task done
# zaf 1: the base conflicts, or the forge refused
# zaf 2: a backend failed
# zaf mode: 750
# zaf group: team, release
# zaf target: task
# zaf phases: land
# zaf timeout: 10
set -e
zaf do --tier machine merge-base "$ZAF_SLICE" "$ZAF_BASE"
zaf do pr-merge "$ZAF_PR"
zaf board done "$1"
```

| Key | Required | Meaning |
|---|---|---|
| `description` | yes | one line, what `zaf do` prints beside the name |
| `<n>` (a non-zero integer, never `125`) | at least `1` | what that exit code means; every code the body can return is declared |
| `mode` | no | three octal digits, as a file's; default `755` |
| `group` | no | the roles the mode's group digit covers, comma-separated; default none |
| `target` | no | what the first argument names: `task` (its phase is checked) or nothing; default nothing |
| `phases` | no | the Team Phases the action may run in, comma-separated; default any; requires `target: task` |
| `timeout` | no | minutes before the run is killed; default `[actions] timeout_minutes` (30), and none for a `terminal` action |
| `kind` | no | `model` (running it starts a model and costs the task's size), `wait` (it waits on the outside and costs nothing) or `zaf` (zaf runs it alone and it costs nothing); any other value, or the key twice, is refused; optional for an action no phase list names (§5.1) |
| `ends` | whenever `kind` is set | the fact that ends the phase: `pr-open`, `review-posted`, `ci-done`, `merged` or `exit` (the phase's process exited 0); one value, refused without `kind`, and any other value, or the key twice, is refused naming the five (§5.1) |
| `on-fail` | no | an action name, only with `kind: wait` or `kind: zaf`: the model action the tick starts when the phase fails on something a programmer can answer (§5.1); without it a failed wait raises a question on its task; `zaf doctor` names one that resolves to no action or to one whose kind is not `model` (§5.1) |
| `terminal` | no | `yes`, the only value: the body keeps the terminal of whoever runs it (below, **On the terminal**); refused beside `kind`, since a phase runs with no one there; any other value, or the key twice, is refused |

The phase keys, written as an action file carries them: `# zaf ends: pr-open | review-posted | ci-done | merged | exit` and `# zaf on-fail: <action>`. The parser holds them as `ActionMetadata.ends: Option<PhaseEnd>` and `ActionMetadata.on_fail: Option<ActionName>`.

A file with no metadata, no description or no declared code, or one that declares `125`, is refused by `zaf do` (`NOT_RUN`, exit 125, naming the line) and reported by `zaf doctor`. A comment marker is any run of non-alphanumeric characters (`#`, `//`, `--`, `;`, `REM`), so the format is the same in every language.

**Modes.** Three subjects: *owner* is the Engineer (a hand run, no `ZAF_INSTANCE`); *group* is the roles the action names; *others* is every other role. Three bits: `r` (4) the action is listed by `zaf do` and shown by `--show`; `w` (2) it may be overridden by a file in a higher tier, which only the owner digit can say, since the Engineer writes those files (`7xx` can be shadowed, `5xx` cannot); `x` (1) it may be run. A shadowing file never widens the run bits of the file it shadows, whatever mode it declares. The caller's class comes from `ZAF_INSTANCE`'s role and passes through nested `zaf do` calls. A run the mode refuses prints `NOT_RUN <name>: not permitted for <role>` and exits 125; a listing shows only what the caller may read; `zaf doctor` validates every mode and group. Modes guard against mistakes: `ZAF_INSTANCE` is an environment variable a process can set, so the guard that holds is the phase.

**Team Phases.** A task's phase is state zaf derives, never reads from the environment: from the board (labels, the claim comment), from the forge (the head of the recorded pull request), from the workspace (its latest commit) and from zaf's own records (the slice, the check records). An action with `target: task` and `phases:` runs only while the task its first argument names is in one of them; outside, `NOT_RUN <name>: #<task> is in <phase>, not <phases>`, exit 125. A board, forge or workspace read that fails while deriving the phase refuses the action the same way, `NOT_RUN <name>: #<task>'s phase cannot be read: <why>`, exit 125, and nothing runs; so does a `.pr` record that is there but cannot be read or holds no number, which is never taken for no pull request.

| Phase | The task is | Derived from |
|---|---|---|
| `claim` | claimed, no slice yet | the `claimed` label and the claim comment |
| `build` | its slice open, a programmer at work (or a fix round) | the workspace and `.zaf/slices/<task>` exist |
| `check` | its task checks have passed on the workspace; a must-fix or a failed step stays in `build`; the team flow may skip it (ruling 39) | the last `zaf check <task>` record, clean |
| `publish` | its pull request open, review steps not yet run | `.zaf/slices/<task>.pr` |
| `review` | the PR's steps have run; a must-fix returns it to `build` | the last `zaf check pr` record |
| `land` | the last `zaf check pr` result for the PR and its current head is clean, and the workspace's latest commit is that head; no result is not clean | that record's head against the PR's head and the workspace's latest commit |
| `done` | merged | the `done` label |

The first rule that holds decides: the `done` label is `done`; a `check pr` record clean for the PR's current head, with the workspace's latest commit at that head, is `land`; a clean record with the workspace ahead of it, or a must-fix record, is `build`, or `check` when a clean task check is newer; a failed step is `review`; a `.pr` record with no result for the current head is `publish`, or `check` when a clean task check is newer than the `.pr` record, or `build` when the last task check failed; a clean task check is `check`; a workspace record is `build`; the `claimed` label with a claim comment is `claim`; anything else is `unclaimed`, which no `phases:` may name.

A fact zaf could not read, because a board or forge read failed, refuses the action with `NOT_RUN`. A fact that is absent, such as a pull request with no head or a missing workspace, falls to the earlier phase, so it can never reach `land`. A claim has no expiry: the spawner hands back a timed-out instance's claims (ruling 41).

**The records.** zaf writes them, never a script. When `slice-open` or `slice-pr` exits 0, zaf stores what it handed back in `.zaf/slices/<task>` (the workspace path) or `.zaf/slices/<task>.pr` (the number). When `slice-merge` or `slice-drop` exits 0, zaf forgets both and the task's check records, so a drop returns the task to `claim` and a reopened slice starts clean. `zaf check` and `zaf changes` read the workspace from the record and fill the base from `ZAF_VERSION` and the branch pattern. These are plain files, so this stops a script's mistake, not a process set on forging them.

**Name.** The file name, as is: `.zaf/actions/land` is `land`. No spaces; hyphens, dots and underscores are fine; no extension is dropped.

**Environment.** Run in the caller's current directory (the project root for a hand run, the slice workspace for a programmer), with `ZAF_ROOT` (the project root), `ZAF_HOME`, `ZAF_ACTION` (the name), `ZAF_DEPTH` (how many `zaf do` calls are above this one), `ZAF_BASE` (the integration branch, from `ZAF_VERSION` and the branch pattern) and `ZAF_INSTANCE` and `ZAF_VERSION` passed through. A `target: task` run also has `ZAF_SLICE` (from the task branch pattern), `ZAF_PR` (from the record, when one exists) and `ZAF_TASK_TITLE` (from the board). A manifest `[env]` table applies to every action run but can set none of these. Arguments after the name go to the body as given.

**Handing a value back.** An action that stands in for a verb's step hands its value back as the last non-empty line of its log: `pr-open` a pull request number, `commit` a commit id, `slice-open` the workspace path. `merge-base` exit 1 means conflicted, with the paths in the log; any other non-zero is a backend failure.

**Output and exit.** Everything the body writes, stdout and stderr, goes to `.zaf/logs/<DATETIME>_<ZAF_ACTION_NAME>.log` (`~/.zaf/logs/` outside a project), `<DATETIME>` as `YYYYMMDDTHHMMSSZ`. On exit 0 `zaf` prints nothing. When the body ran and exits non-zero, it prints `FAIL <name>: exit <n>, <its declared meaning>, log <path>` and the last ten lines of the log; an undeclared code prints `exit <n>, undeclared`. The code passes through unchanged. A run past its time bound did run, so it is `FAIL`, exit 2. When the body never ran (§5), it prints `NOT_RUN <name>: <reason>` and exits 125. A body that exits 125 because a nested action did not run is `FAIL`, `exit 125, a nested action did not run`, and the code passes through. `--more` prints the whole log after the run; `--json` gives result (`OK`, `FAIL` or `NOT_RUN`), name, tier, exit, meaning, seconds and log. A nested `zaf do` writes its own log and its path into the outer one. A `zaf check` step that runs a process logs the same way (ruling 30).

**On the terminal.** An action that declares `terminal: yes` holds a conversation with the person at the terminal. Its body gets zaf's own stdin, stdout and stderr, and stays in zaf's process group, the one the terminal lets read. While it runs zaf ignores Ctrl-C and Ctrl-\, so the keys reach the body and zaf stays to report. Its log holds one line saying it ran on the terminal, then the path of each nested run. A `FAIL` prints its line and quotes nothing from the log. Only a `timeout` the file declares bounds it. When zaf's stdin or stdout is not a terminal, as in a model's shell, a pipe or a detached launch, it prints `NOT_RUN <name>: it needs a terminal, and this run has none` and exits 125, so no model runs it. A hook never runs on the terminal: one that declares the key is `NOT_RUN`, and `zaf doctor` names it. A `zaf check` step and the tick's `zaf` actions run with no terminal. `zaf do --json` shows `"terminal": true` on such an action.

## 4. The verbs, as compositions

Each verb keeps its name, its exit codes and its logic; the steps where it shells out are names the project or the machine provides. A step with no action exits 2, `missing action <name>`.

| Verb | Stays in zaf | Named steps the project provides |
|---|---|---|
| `board ready\|claim\|report\|question\|ruling\|done\|file` | leases, states (labels, or a Project field), comment markers, through the Board port; `done <task>` sets the `done` state, drops `ready` and `claimed` and closes the issue as completed (an open issue that carries `done` still reads as done), and refuses unless the task is in `land` or the pull request recorded for it has merged; `file <epic> <title>` opens a task under the epic in the task template, ready or `--blocked`, and files a title the epic already counts only once | none: the board is state, not a step |
| `ask`, `asklog` | the ladder, the quote check, the log | none |
| `brief` | the pack's composition; **it lists the project's actions** | none |
| `check <task>` / `verify` | the engine, the dedupe, the record, the phase it records | `gate-light` and `test <name>` when the manifest names them as actions; a `[check.*]` step may be `action:<name>` beside `command:<cmd>` |
| `check pr:<n>` | waiting on CI, bots and runners; the record with the PR's head | `action:<name>` steps |
| `forge open\|merge\|checks\|head\|log` | the forge's writes and the reads around them, through the Forge port, for whichever forge `[forge]` names (assumption 24): `open <head> <base> <title> <body>` prints the new pull request's number, or the open one's, saying so on stderr; `merge <pr> [--squash] [--match-head-commit <sha>]` prints nothing, merged now or before, and says `not mergeable yet` for a merge the forge cannot make yet; `checks <pr>` prints `<bucket>\t<name>\t<link>` per check of the head, the bucket `pass`, `fail`, `pending`, `skipping` or `cancel`; `head <pr>` prints the head commit, or nothing; `log <name> <link>` prints a failed check's last 80 failed log lines under a line naming it, or its link on a forge with no log API, or nothing when the link names no job. A refusal is exit 1, a backend failure (no `[forge]` among them) exit 2 | none: they are the steps `pr-open`, `pr-merge` and `ci-wait` call |
| `changes` | the VCS port's diff, stat before hunks | none now |
| `slice open` → `zaf do slice-open <task>` | nothing: the project's action; `zaf slice open` is its alias one release | `workspace-open <slice> <base>` |
| `slice pr` → `zaf do slice-pr <task>` | nothing: the project's action | `commit <slice> <message>`, `push <slice>`, `pr-open <slice> <base> <title> <body>` |
| `slice merge` → `zaf do slice-merge <task>` | nothing: the project's action, `phases: land` | `merge-base <slice> <base>`, `push <slice>`, `pr-merge <pr>`, `workspace-drop <slice>`; no `gate-light`, CI is the gate (ruling 39) |
| `slice drop` → `zaf do slice-drop <task>` | nothing: the project's action | `workspace-drop <slice>` |
| `spawn`, `spawn trace`, `status`, `guard`, `report` | all of it | none |
| `doctor` | the manifest's validator; **it checks every action** (metadata, modes, phases, runnable, shadowing, each needed name provided) | none |
| `setup`, `profile init` | they write the project's own files; `setup` makes the two homes (§2); in a folder with no manifest `setup` asks four questions (project name, board repo, forge repo, gate command; each offers the value it can work out) and writes `.zaf.toml` with the standard values a tick needs, the `[requires]` tools and the `[forbidden]` merge denies among them (ruling 49); when `origin` is not a GitHub remote it takes the host for a Forgejo instance, offers the remote's `owner/name` for the two repos, asks one more question, `forge url`, offering as its default the first of a few candidates built from the host (the remote's own address when it is http, then `https://<host>`, `http://<host>:3000`, `http://<host>`) that answers `GET /api/v1/version` within a few seconds (no default when none does), and writes Forgejo's kinds with `url`, `repo` and `token_env = "FORGEJO_TOKEN"`, with no `gh` in `[requires]` or `[forbidden]`; with no `origin` it asks no URL and writes GitHub's kinds; its doctor run asks the backends too, so a missing token variable fails it and says what to export, and in a folder that has one it asks nothing and overwrites nothing; it then generates the profiles (what `profile init` does, which stays as its own verb) and installs the pack's standard actions into the machine tier (§2); the `init` verb is retired into it (ruling 49) | none |
| `[gate]` | the gate port keeps its levels; a line may be `zaf do gate` | the profile allow-list derives its tool rules from a literal line, so a project that wants both keeps the line |
| `[runners.<name>]` | the template and its placeholders | none now |

The release brief's "merge and tag" is the project's `release` action, which squash-merges with `pr-merge <pr> --squash`; the Engineer's hand-made PR lands with `zaf do land <pr>`. `pr-merge` takes the pull request and one option, `--squash`: with none it merges with a merge commit, and any other option is refused, exit 1. `[check.pr]` may name `action:<name>` instead of a line; ways' own is `["ci"]` (ruling 39). The jj code the slice verbs used leaves zaf for the project's scripts; the Vcs port keeps what `changes` needs. The forge's calls stay behind the Forge port as the `zaf forge` verbs, so `pr-open`, `pr-merge` and `ci-wait` run unchanged on GitHub and on Forgejo; on GitHub each verb makes the `gh` call the action made before.

## 5. The verb added

| Verb | Use it to |
|---|---|
| `zaf do` | list every action the caller may read: name, tier, description; `--json` for the spawner and the briefs |
| `zaf do <name> [args…]` | run one; its exit code, its meaning on failure, its log |
| `zaf do --show <name>` | print the file a name resolves to |
| `zaf do --tier machine <name> [args…]` | run the machine's action when the project's shadows it; modes and phases apply as ever |

`zaf do <name>` exits `0` when it is done (`OK`). It exits `125` when the body never ran (`NOT_RUN`): no such action, a file without metadata or not runnable, a mode or phase that refuses, an action that needs a terminal where there is none, or a file that could not start. Otherwise the body ran (`FAIL`): the action's own declared code, or `2` for a timeout. No action may declare `125`, and `zaf doctor` rejects a file that does, so a caller never reads a refusal as a declared code such as `merge-base`'s `1`, conflicted. Every other verb keeps `0`, `1` and `2`, and a verb's step with no action stays exit 2, `missing action <name>` (ruling 17).

**`zaf hub`.** The Engineer's live view of what is happening. It only reads: it starts nothing, changes nothing and costs no model turns.

```
epic #103                     [######------------------------]  17 of 82       $39.83
  1 of 2 slots free · 63 ready · no questions

group: ways-steps             [##########--------------------]  3 of 9
  #143  sonnet programmer     [#################-------------]  build    testing        40s
  #156  opus team             [##########################----]  review   waiting on CI   2m
```

An epic and a group count their tasks done. A ticket's bar is its Team Phase, one of seven, because a model has no honest percent. A group is a task's `group:<name>` label. In a project with `[phases]`, a ticket's state, the `ready` count and the queue come from where the core places each ticket (§5.2), not from its label, which the tick sets from that place anyway (§5.1, step 2); a ticket the core does not place shows its label. A ticket's word is general, from its last tool call: reading, writing, testing, waiting on CI. The time is since its last report and keeps ticking, so silence shows.

It redraws when a report arrives, not on a timer. zaf verbs report that state changed and a hook in the profiles reports each tool call, so no model spends a turn reporting its tool calls. Between reports only the clocks move and nothing reads the network. Outside a terminal it draws one frame and exits, so a model cannot hang on it.

**Model phases.** Each model declares its own phases when it starts, `zaf progress plan <task> <phase>…`, and reports each change, `zaf progress at <task> <phase>`. Phases may repeat: a model that goes back from `test` to `write` reports `write` again, and its row shows the iteration, `write ×2`. The ticket row keeps its Team Phase bar, and each model reporting on the ticket gets a row under it with a bar over its declared phases. Each phase report is a hub report, so the frame redraws. It costs the model one turn per phase change, which ruling 44 accepts.

**Dashboard mode.** `zaf hub --port <n>` serves the same frame as an HTML page on every interface at that port, for anyone on the LAN. Reading is `GET`, asks for no login and changes nothing; a control is a keyed `POST` (the JSON interface, below). It prints the page's LAN URL when it starts, and, started from a terminal, the link that carries the key under it. `--read-only` serves the page with every control refused. The page holds a server-sent events stream and redraws when a report arrives, so it is never staler than the terminal. It runs until it is stopped. The terminal frame is unchanged by any of this.

**The hub's JSON interface.** The hub answers JSON under `/api/` on the dashboard's port. It is the contract the change stream, every control and the page follow; a route listed here that no task has built yet answers as an unknown route does.

| Route | Answers |
|---|---|
| `GET /` | the page (HTML) |
| `GET /events` | the frame's server-sent events stream, one event for each hub report (unchanged) |
| `GET /api/state` | `200`, `application/json`: the whole machine state, read anew for each request |
| `GET /api/events` | the change stream: a server-sent events stream with one event whenever a report arrives or an instance starts or ends |
| `POST /api/tick` | a control (below): one spawner tick for a project, with the version remembered for it |
| `POST /api/stop` | keyed; body `{"project": <a listed project's root or name>, "task": <number>}`: ends the task's running instance and releases its claim, as `zaf spawn stop` does from that project's root; `200` with that verb's `--json` (`task`, `stopped`, `released`); a task with no live instance is `409`, a body that is not that `400` (`411` with no `Content-Length`, `413` over 4 KiB), a project the list does not hold or holds as missing `404`, a backend that failed or an instance that would not end `500`, each in the refusal's shape with its reason, and nothing changed |
| `POST /api/watch` | a control (below): starts or stops a project's watch, the loop `zaf spawn --watch` runs, inside the hub |
| `POST /api/<control>` | one route for each control; a control carries the hub's key in `X-Zaf-Key` (below), and each control task writes its own route down here |

Every answer is sent `Cache-Control: no-store`. A path under `/api/` that is not listed is `404`; a method a route does not take is `405` with an `Allow` header naming the one it takes, and a `POST` to `/api/state` is such a request: it changes nothing and reads nothing. A request the server has no room for is `503`, a head over 8 KiB `431` and one that is not HTTP `400`; outside `/api/` these answer in plain text.

**The refusal.** Every refusal under `/api/` is `application/json`, an object with one field, `refused`, in plain words: `{"refused": "GET only"}`. A refusal carries no other field, so a caller shows the sentence and branches on the status. `503` is also what `GET /api/state` answers when the machine has nothing to read (no zaf home), saying so.

**The guard.** When the hub starts it makes a key, 256 random bits from the system's random source written as 64 hex digits, and keeps it in memory only: it is never written to a file, a log, a run folder or the page's source, and no `Debug` print shows it. Every `POST` to a path under `/api/` that is not a read (`/api/state` and `/api/events` answer GET only) is a control, and the hub asks for the key before it gives the request any work: the key is the value of the `X-Zaf-Key` request header, compared with the hub's in constant time. A request with no key or the wrong one is `403` in the refusal's shape (`{"refused": "a control needs the key this hub made when it started, in the X-Zaf-Key header"}`) and changes nothing, whether its route is built or not. The key is read from the header alone, never from the path or the query, which a log would keep; a method other than `POST` to a control stays `405`, so a browser's preflight on another origin fails. `zaf hub --port <n> --read-only` (it needs `--port`) serves the page and every read as before but refuses every control `403` whatever key it carries (`{"refused": "this hub is read-only: it serves no controls"}`). `GET /api/state` tells the page which hub it is in its `controls` field. Started by hand, with a terminal on its output, the hub prints the link `http://<address>:<port>/#key=<key>` on a second line, `controls: <link>`; the key rides in the link's fragment, which a browser keeps and never sends in a request, and the page reads it from there (the frontend's). With no terminal (a service, a pipe, a file) nothing prints it, and a read-only hub prints no link.

**`POST /api/tick`.** Body (JSON, at most 4 KiB): `{"project": "<root>", "version": "<v>"}`; `project` is a project's `root` as `GET /api/state` names it, and it must be on the zaf home's list, so no other folder is ever ticked; `version` is optional, a milestone of letters, digits, `.`, `-`, `_` and `+` (never a leading `-`). The version is remembered on the project's entry in `projects.toml` (`ProjectEntry.version`) and is asked for again only when none is remembered; one given replaces the remembered one. The tick is `zaf spawn --once --no-wait --version <v>`, run as a process in the project's root with `ZAF_INSTANCE` and `ZAF_RUN` removed, so it is the same app code (a running scheduler is asked for the tick instead, as the verb does). The hub waits for it at most 60 seconds and then answers, leaving the tick and the models it started to run on. `200`: `{"version": "0.4.0", "running": false, "tick": ["<line>", …]}`, the tick's own words, which name what it started, held back and skipped (`started implement #4: 1 units`); `running` is true when the tick had not ended, and `tick` is what it had printed, which already holds what it started. Refusals, in the refusal's shape: `400` for a body that is not a request, a version that is not one, or no version when none is remembered (`a version is needed: none is remembered for <root>; send version once`); `404` for a project not on the list; `409` for a project whose folder or manifest is gone, or a tick the verb refused (exit 1: a stale profile, a scheduler of another milestone), with its words; `413` for a body over the limit; `502` for a tick that failed (exit 2 or other); `503` when the machine has no zaf home; and `403` without the key, as for every control.

**`POST /api/watch`.** Body (JSON, at most 4 KiB): `{"project": "<root>", "action": "start" | "stop", "version": "<v>"}`; `project` as for `POST /api/tick`, on the zaf home's list; `version` only with `start`, remembered and asked for as `POST /api/tick` does. A start runs the scheduler's loop (§5.1) for the project on a thread of the hub's own process, with the hub as the holder of `.zaf/scheduler.lock`, so the tick record's `watch` flag reads true: its first tick runs at once, then one on each request in `.zaf/tick.request` and each `[spawn] tick_minutes`. Each tick is `zaf spawn --once --version <v>`, run as a process of its own in the project's root, with `ZAF_INSTANCE` and `ZAF_RUN` removed and `ZAF_SCHEDULED_BY` naming the hub's pid, which tells that `--once` the tick is the scheduler's own, so it runs and does not ask the scheduler for one. A project a scheduler already runs for, the hub's own or a `zaf spawn --watch` in a terminal, refuses a second start. A stop asks the hub's own watch to end after its current tick, which the hub waits for up to 20 seconds; a scheduler another process holds is never stopped from here. Every watch the hub started ends when the hub does: dropped with its owner at the hub's end, or with the process, whose end lets go of every lock. `200`: a start `{"project", "action": "start", "watching": true, "version", "since", "tick"}`, a stop `{"project", "action": "stop", "watching": false}`; `202` for a stop whose tick still runs (`"watching": true`, `"stopping"`: it ends once the tick has). Refusals, in the refusal's shape: `400` for a body that is not a request, an action that is neither, a version that is not one, or no version when none is remembered; `404` for a project not on the list; `409` for a start beside a scheduler that runs (with where it runs), a stop with no watch of the hub's to stop (naming a scheduler of another process, when there is one), a start once the hub is ending, or a project whose folder or manifest is gone; `500` when the lock or the thread could not be had; `503` when the machine has no zaf home; and `403` without the key, as for every control.

**`GET /api/state`.** An object with four fields. Names are snake_case, a time is RFC 3339, and a field that holds nothing is `null`, never absent, unless its entry below says otherwise.

- `controls`: `true` for a hub that serves controls, `false` for one started with `--read-only`, where every control is refused; the page shows its buttons only when it is `true`.
- `machine`: the headline across all projects: `instances` (the instances running now), `projects` (the projects on the list, missing ones included), `in_use_units` (a number: what the machine's instances use, in units) and `budget` (`units`, the machine cap or `null` for none; `reserve`; `sizes`, the cost of each size, keyed `XS`, `S`, `M`, `L`, `XL`).
- `next`: the Next for you list, derived from the same read, most blocking first, empty when nothing waits on the Engineer. Each item: `kind` (`sign`, `question`, `door`, `unticked`, `failed` or `broken`), `project` (its name), `title`, `blocks` (the tasks it holds back), `how` (a sentence or two), `link` (where a person opens it, or `null`) and `command` (the command that does it, run as written, or `null`).
- `projects`: every project on the zaf home's list, in the order they joined, missing ones too. Each: `project` (its name), `root`, `missing`, `gathered_at`, `reason` (why part of it is missing, in plain words, or `null`), `epics`, `queue`, `questions`, `problems`, `instances`, `watch` and `last_tick`.
  - `epics`, each: `number`, `title`, `stage` (`unsigned`, `signed`, `planned`, `challenged` or `done`), `url`, `done`, `total`, `dollars` and `groups` (each `name`, `done`, `total`).
  - `queue`, each task ready, claimed, blocked or waiting on a question: `number`, `title`, `epic`, `state` (`ready`, `claimed`, `blocked` or `question`), `group`, `instance` (for a claimed task), `phase` (its Team Phase, for a claimed task), `issue_url`, `pull_request`, `pull_request_url`.
  - `questions`, each: `number`, `raised_on` (the issue it was raised on), `text`, `door` and `url`.
  - `problems`, each: `kind` (`manifest`, `token`, `board`, `profile` or `missing`), `detail` and `fix` (a command, or `null`).
  - `instances`, each: `instance` (as `<role> instance <n> on #<epic>`), `role`, `task`, `number`, `title`, `phase`, `run_seconds` and `last_tool_call`.
  - `watch`: `running`, `pid`, `since`, `zaf`, `version` and `last_tick`, or `null` for a project that could not be read. `last_tick`: `at`, or `null` before the first tick.

A project whose board cannot be reached is not an error: it comes back with its `reason` and what could still be read. A project whose read does not answer within 30 seconds shows that as its `reason`, so no project holds the others up. Reads of the machine state go one at a time, and the requests that arrive while one runs share it, so a crowd of requests costs the boards one read.

**`zaf status`.** In a project with `[phases]`, `ready` is the tickets in the lane, as the core places them (§5.2), and the tickets the core does not place that are labelled `ready`; with `--more` each lane ticket follows with its next action (`  #3 implement`). A `waiting` line counts the tickets that wait (`waiting   2 (#5 #9)`), and `--more` names what each waits on in the trace's short form (`  #5 waiting(question #45)`). `--json` carries the same, as `lane` and `waiting`. A placement that cannot be read is a warning on stderr, and the rest of the screen prints as before, from the labels.

### 5.1 The phase scheduler

Designed for 0.3.0 by epic #421, ruled by the Engineer on 2026-11-10 (§8, rulings of #421 and of the questions raised on it). zaf schedules a task's phases and a model is a worker for one stretch of a task: it runs until the first wait on the outside, then exits and frees its budget, and zaf starts a fresh model for the next phase later. zaf decides and an action does. The tick, the choice of what runs, the budget and the lock stay in zaf; what a phase does is an action, and some start a model while others do not. The team instance goes away: each phase action launches the worker it needs directly (a programmer to implement, a reviewer to review), and zaf does the coordinating. These phases are a task type's own, and are not the Team Phases of §3, which still guard `zaf do` and are derived as before; nor the phases a model declares to the hub (§5).

**A task's phases.** A task type has an ordered list of action names, its phase list, and zaf owns it. The project manifest declares one list for each task type, in a `[phases]` table keyed by the type's name, and a ticket's Type (the forge's issue type, such as Task or Bug) picks the list. A higher manifest layer replaces a type's whole list, as §6 and assumption 11 say of an array. The load refuses an empty list and a name listed twice, and `zaf doctor` names a listed action that no tier provides, one with no kind and one with no `ends`. A task with no type, or a type with no list, is named by the tick and passed over. Phases of one task with no wait between them stay in one model run: a task that reads its brief and then implements is one model, not two (ruling 2), so adjacent model actions form one run named by the first.

**Kind, ends and on-fail.** Each phase action declares three things in its metadata (§3), and zaf reads them and guesses nothing (ruling 23).

| Key | Value | Meaning |
|---|---|---|
| `kind` | `model` | running it starts a model and costs the task's size |
| | `wait` | it waits on the outside, with or without a process of its own, and costs nothing |
| | `zaf` | zaf runs it alone in the tick, with no model, and it costs nothing |
| `ends` | `pr-open`, `review-posted`, `ci-done`, `merged` or `exit` | the fact that ends the phase: one of four the forge answers, or `exit`, the phase's process exited 0 and raised no question; required whenever `kind` is set, refused without it |
| `on-fail` | an action name | only on a `wait` or a `zaf`-kind action, optional: the model action the tick starts as the task's phase when the phase fails on something it answers, at the task's size; when it exits, the phase applies again to the new head |

A review can be either a reviewer model or a wait on the outside, by its action's kind, and zaf does not choose. A wait is failed when a check failed at the pull request's head or when its own run at that head exited non-zero. A failed wait that declares no `on-fail` raises a question on its task (the ruling on #425), so the Engineer decides what follows. The key was proposed as `on-red` and ruled as `on-fail`. An `on-fail` answers only what a programmer can (`Failure::for_on_fail`): a check failed at the head, the run exited 1 (every action's canonical failure: a must-fix, a red check, a conflict), or it exited 0 and still failed, which a counted run does when it raised a question that is now ruled. Any other code is the phase's own, a backend that failed or a refusal no change answers: a `zaf`-kind phase runs again, until it gets nowhere, and a wait raises the question of a wait with no `on-fail`. A ruled question reaches the `on-fail` once: when a run of the `on-fail` began and ended at the head after the run that raised it, exited 0 and raised none, the phase is open again and applies anew, so a fix that finds nothing to change is not run until it gets nowhere.

**Review, CI and merge.** Review is a wait the launcher runs with no model: it runs `zaf check pr` at the pull request's head as its own detached process, with no budget, ends at `review-posted`, and its `on-fail` is the fix action, a model (the ruling on #452; the challenger's proposal of a model review is declined). `ci` is a wait that ends at `ci-done`. `merge` is a `zaf`-kind action that runs `slice-merge`, which needs a clean `zaf check pr` at the head; its `on-fail` is `fix`, and it tells `slice-merge`'s exit 1 apart: 1 is a base that conflicts with the slice, its paths on one line last in its log; 3 the base merged into the slice and pushed, which moves the head, so CI and the review run again there; 4 a refusal (the forge's, or a head that moved since the check). A model is started only when CI is red, the review has findings to fix, or the base conflicts (ruling 6), so ci never starts one and merge only for a conflict.

**Where a ticket sits.** Each tick places every open ticket whose type has a phase list (`Board::open_tickets`: the open tasks not labelled `done`, whatever their state label), and nothing about the queue is stored (ruling 5). The scheduling core places it (§5.2) from the forge, the phase run folders and the questions open on the ticket or its epic. A ticket sits in exactly one place, the first of these that holds:

1. **Running:** a phase run of it is live (its process is alive and has recorded no exit), whatever else holds. A run whose process died holds nothing.
2. **Waiting on its epic:** the epic is not signed, or not challenged yet.
3. **Waiting on a question:** a question is open on the ticket or on its epic, including one its own run raised.
4. **Waiting on a ticket:** a ticket it names in `Blocked by:` is not done.
5. **Waiting on a check:** the list has a `ci-done` phase and the checks at the pull request's head have not all ended; none registered counts as not ended. A current phase that awaits the outside after its run exited 0 waits here too.
6. **In the lane:** none of the above, with its next run (the current phase, or its `on-fail` when the phase failed on something the `on-fail` answers) and since when.

A waiting ticket waits on every one of these that holds, and comes back to the lane only when none does. A ticket whose pull request is merged, or every phase of which has its end fact, is done; a ticket labelled `done`, or closed, is not among the open tickets at all, so it is never placed or started again. No state label is read: a ticket labelled `blocked` whose blockers are done is in the lane, and one labelled `ready` whose blocker is open waits; the tick then sets its label to match (step 2). The current phase is the first listed one whose end fact does not hold for the pull request's current head (the ruling on #424), so a push that moves the head reopens a review posted at the old head, and after a push nothing starts until the checks at the new head have ended.

**One gate for both paths.** The tick and `zaf spawn phase` start a phase through one function, `may_start` (`app/schedule/tick.rs`), which asks the core where the ticket sits and lets an action start only when the ticket is in the lane at that action, the wait it failed is not one with no `on-fail` to answer it (none named, or a failure the `on-fail` does not answer), and the action is not getting nowhere (step 5). `zaf spawn phase <task> <action>` gathers the ticket as the tick does and refuses, exit 1, in the gate's words: the ticket is not open, a phase of it already runs, every phase is done, it waits (on what, in words: `its epic #7 is not signed`, `a question is open on it`, `#4 is not done`, `the checks at h1 have not ended`), another action is next, or the action got nowhere three times. A started ticket is held like any other: a question on its epic or an unsigned epic stops its next start, never a phase that runs. A ticket the tick skips is refused in the words the tick names it by, through the same read: a ticket that is not a task of an epic has no signature to run under, so it does not run; the tick names it among the tickets it could not read (`skipped #3: it is not a task of an epic`) and goes on with the others, and `zaf spawn phase` refuses it, exit 1, `#3 cannot start: it is not a task of an epic`. A ticket something about which cannot be read fails `zaf spawn phase`, exit 2, `#3 cannot be read: <why>`. For a `model` action `zaf spawn phase` also counts the slots under `spawn.lock`, as step 6 counts them, and refuses, exit 1, `#4 cannot start implement: every slot is in use (4 of 4)` when none is free, so two starts that each saw the last slot free never go one over. An inline `zaf`-kind run passes the same gate again under `spawn.lock` just before its run folder opens (step 3), so two ticks that read the lane at once never run the same action twice.

What the current phase's latest run at the head meant comes from what the run left, not from its exit code alone (R13). A question it raised that is still open makes the task wait on it, whatever the code. The phase's fact holding is done. A run that exited 0 in a phase whose fact comes from outside (a review, CI, a merge) waits for it. Anything else failed: a failed wait or `zaf`-kind phase with an `on-fail` that answers the failure starts it, a failed wait with none to answer it is failed for the question of step 5, and any other failed `model` or `zaf` phase is ready again. A run that never ran its body (exit 125), was stopped by a signal (128 and above) or died with no exit code is not counted, so the phase runs again, and a wait whose run died is launched again. While the list has a `ci-done` phase and the checks at the head have not all ended, none registered included, the task waits and nothing is next. So `ci` itself is never launched: green ends it and red fails it to its `on-fail`. `since` is when the phase failed, or else when the previous phase's fact came to hold, or when the task became ready for its first phase, and it is the task's weight (ruling 20), with its priority's worth added (**Priority**, below). When the task became ready for its first phase is read from the board, with nothing stored: the latest of when its issue was opened and when its last done dependency was closed. The ruling time of a question on it or its epic is not read, since the board gives no ruling time and the questions on a ticket are a list read of their own; with neither time, the tick's own time stands in, as before. A wait is ready until it has run at the current head, then waiting until its fact holds, and a wait already run at the current head is not launched again. A forge read that fails makes the ticket unreadable, named, and it is skipped that tick; zaf never guesses a place. That includes the read of whether the pull request changes a file, and the read of the pull request record itself: a `.zaf/slices/<task>.pr` that is there but cannot be read or holds no number makes the ticket unreadable, never a ticket with no pull request, which would start implement again over an open one.

The `exit` fact holds when a run of the action exited 0 and raised no question. A run that asked one is never done by its exit code, even once the question is ruled: it runs again, with the ruling to go on. For a phase listed after the one that carries `pr-open`, the run must also have left the pull request's current head; one listed at or before it holds whatever head the run left, so a fix pushed later does not reopen it. A list with no `pr-open` phase keys every `exit` on the head. `pr-open` holds once the recorded pull request changes at least one file, so an empty one does not end the phase that opened it. The launcher that started the phase writes the code into the phase's run folder when the process ends, and the placement reads it (the ruling on #451). The code is a recorded act that ruling 47 keeps alongside the launch record, and the queue is still derived from it and never stored. A phase run folder holds the task, the action, the pull request's head when it started (empty without one), the pid and, once the process has ended, the exit code; a dead pid with no exit code reads as no exit code, never as 0. Once the process has ended the launcher reads the pull request's head and records it as the folder's `head-end`, the head the run left, before the exit code, which is still written last: `head-end` is empty when the task has no pull request, and absent when the head could not be read, which reads as unknown and never counts toward getting nowhere (§5.2); the exit code is written all the same. A question `zaf board question` raises inside a phase run (`ZAF_RUN`) on the run's own task is appended to the folder's `questions`, one issue number per line; outside a run nothing is written. A `zaf`-kind action the tick runs inline leaves the same folder, opened before it runs under an instance number of its own, with no pid, since it is a step of the tick's own process, and ended with what `zaf do` printed as its `output`, the head it left and its exit code; its body runs with `ZAF_RUN` set to that folder, so a question it raises on its task is recorded there too. `app/schedule/record.rs` is the one place that writes a folder and reads it back; a folder written before these files were kept still reads, and one with no `head-end` is read as having left the head it started at.

**Claims.** Ruling 47's claim, which counts only while its instance runs, would release a task whose model exited at a wait. A task with a recorded pull request is held by its forge facts, not by an instance, so its claim stays until the task is done; the orphan release applies only to a claimed task with no pull request and no running phase (the ruling on #426). A running phase holds its task too, and so does a `.pr` record that cannot be read: no claim is released on a read that failed. `zaf status` shows an orphan by the same rule. `zaf spawn phase` releases the task's own claim by the same rule before it starts, as the tick does before it plans, so a second run can claim a task whose first instance has ended.

**The tick.** A tick derives, it does not store, and it never waits for a phase. Each tick, in this order:

1. The `pre-tick` hook runs; a non-zero exit fails the tick (ruling 11).
2. It derives every epic's stage (§8, ruling 48). Then the tick gathers every open ticket with a phase list once and places each (above), and sets each open ticket's state label from where it sits (R5), writing only a label that differs: a ticket that waits on a question and carries `ready` gets `question`; one that waits on another ticket, and on no question, gets `blocked`; one that carries `question` or `blocked` and waits on neither gets `ready`. The label is output only: placement never reads it. The claim owns `ready` and `claimed`, so the tick never sets one over the other and never writes over `claimed`; it never sets or clears `done`, and leaves a running ticket and a done one as they are. A ticket labelled `blocked` that waits on a question keeps `blocked`, since a board sets `question` only over `ready` or `claimed`. A ticket the tick does not place (its type has no phase list, or the project has no `[phases]`) is labelled the same way from the questions open on it or its epic and from its `Blocked by:` blockers, each read once a tick; a blocker still open keeps its task blocked, and so does a dead one (no such issue, a pull request, or closed as not planned), which never closes. A `blocked` task set `ready` is a line of what the tick did (`#26 unblocked: #25 is done`, `#9 unblocked: #5, #6 and #7 are done`, `#9 unblocked: it names no blocker`) and an entry of `unblocked` in `--json`; any other label set is a line `#7 labelled question: it waits on question #45` (`labelled blocked: it waits on #5`, `labelled ready: no question is open on it`) and an entry of `relabelled` (`task`, `from`, `to`). The dry run prints the same lines and sets nothing. A read or a write that fails is named among the tick's failures (`cannot unblock #26: …`, `cannot label #7 question: …`), exit 2, and the other tickets and the tick go on; a tick that cannot gather sets no label. Each ticket that waits on its epic or a question is named in the tick's skipped lines with the first reason that holds (`#3 skipped: its epic #7 is not signed`, `a question is open on its epic #2`, `a question is open on it`, `its epic #7 is not challenged yet`), started or not, and is no error. Steps 3 to 6 walk the lane, lowest ticket first, and pass each entry through the gate.
3. It runs every `zaf`-kind action in the lane, such as merge, one after another with `zaf do`, at no cost to the budget; one that fails is logged and its task is left for the next tick, and the others still run (rulings 6 and 22). Before each one runs, the gate is asked again under `spawn.lock`, the ticket gathered afresh: a ticket no longer in the lane at that action, because another tick's run of it has begun or it moved on, runs nothing (`zaf spawn: NOT_RUN merge on #7: <why>`, exit 125, which never counts toward getting nowhere). The run folder then opens under the lock with an `inline` mark naming the tick's own process, so the run reads as running from its first moment until its exit is written, and once the action's body has started its process is recorded beside it (`inline-body`): the body runs in a process group of its own and outlives a tick that dies, so the run reads as running while the tick or the body lives.
4. It launches every `wait` action in the lane detached, as its own process, at no cost to the budget, and does not wait for any; one that fails to launch is logged and the others still go (rulings 6 and 22).
5. It raises the scheduler's questions (**The questions**, below), each through `zaf board question`'s one path, which makes the issue wait, and charges nothing. A task whose wait failed with no `on-fail` to answer it gets one, unless it already has an open question. It does the same for an action that got nowhere (R18): the action the ticket is in the lane at, its current phase or the `on-fail` of its failed wait, whose last three ended runs (`NOWHERE_LIMIT`) began and ended at the pull request's current head, or at none with no pull request, whatever their exit code. Done, failed, done, failed at one head is getting nowhere; a run that moved the head is not. A run that never ran its body (125), was stopped by a signal (128 and above), died with no exit code or left an unknown head never counts. Steps 3 and 6 do not run a held action, so a merge the forge refuses three times at one head stops and asks. The question names the action, the head, the exit codes and the last line of the last run's output, which the launcher keeps in the run folder's `output`: `fix got nowhere three times at <head> (exit codes 0, 1, 0); the last line of its log: "…". It is not started again until this is ruled. Last run: <n>.` The count is derived from the phase run folders, never stored; a ruling lets the action run again, counting only the runs after the one the ruled question named (#550), and a question raised before this count (`failed 3 times in a row`) marks its run the same way. A board that cannot list the questions the count needs makes that ticket unreadable that tick. `zaf spawn phase` refuses an action getting nowhere in the same words, and raises no question: the tick does. Step 5 then asks about the waiting tickets and the open epics: a check wait past its deadline, a dead dependency, a cycle, and a planned epic with no challenge. Each question raised is a line of what the tick did, after its `question on` line, naming the question and its cause: `asked #61 on #7: merge got nowhere three times at d962227`.
6. It starts at most one model, and never waits for it (ruling 19). The candidates are the lane's model phases, the failed waits with an `on-fail` among them (whose model action is the phase to start), and the epic launches (the planning instance for a signed epic with no tasks, the challenger for a planned one), all in one order (the ruling on #427). An item's weight is how long it has been ready, read from the forge, plus its priority's worth (**Priority**, below); a signed epic's is the time since its signature and a planned epic's the time since planning ended, with no priority. The tick walks the items by how long each has been ready, the earliest first; each that fits the budget and has its prerequisites met is a candidate, and it starts the heaviest candidate, of equal weight the earlier. The items it passes are pushed back, their weight growing as in priority aging (ruling 20). Starvation stays on raw age: an item ready for 30 minutes that does not fit ends the walk, so nothing ready after it starts, whatever its priority, and a stream of prioritised tickets never starves a big old one. A phase blocked on an earlier phase is passed over (ruling 4). The slots in use are the project's planning and challenger launches and its live model runs, counted from the phase run folders themselves, each by the `kind` its action declares, whether or not its ticket reads this tick: a live implement whose ticket's pull request cannot be read still holds its slot. A wait, a `zaf`-kind run and a run whose process died or that recorded its exit hold none; a run whose action's kind cannot be read holds one. Run folders that cannot be counted start no model that tick, and the tick exits 2; steps 3 to 5 still run.
7. The `post-tick` hook runs, idle ticks included.

**The questions.** Every question the scheduler raises goes through one place (`app/schedule/ask.rs`) and `zaf board question`'s path, which labels the issue `question`. Each ends with a marker, its last sentence, that the tick reads back from the board, so nothing is stored: an open question on the issue that ends with the cause's marker is the same question, and is not raised again; a ruled one with it means the Engineer has ruled on that cause, and it is not raised again either, except getting nowhere, whose ruling starts the count again. A cause on a ticket in the lane (getting nowhere, a failed wait) is not raised over any open question on the ticket, as before. Two ticks can overlap (a `zaf spawn --once` that meets the tick a phase end started, or the moment of a scheduler's restart) and both find a cause with no open question, so each question is raised under `spawn.lock`, waited for as an inline run's opening waits for it, once the open questions are read again under it: a question another tick raised since this tick's first read is found there, nothing is raised, and it is not this tick's (its block, its trace line and the `post-tick` input do not list it). The lock is held for that read and the one question's write, never across the step, and a lock that cannot be taken fails step 5 as a board that fails does, the other steps still running. A wait on a question or on an unsigned epic has no clock: the Engineer already has it.

A head in a question is the full commit id, and seven characters of it in the tick's line; `<n>` is nanoseconds since the epoch. The deadlines are constants, as the 30 minutes of starvation is. A head pushed by hand, with no run that left it, has no time of its own: its clock starts at the pull request's opening or the last check that finished at it, so a pull request older than two hours asks on the first tick after such a push.

**Priority.** The Engineer sets a ticket's priority with a label, `priority/1`, `priority/2` or `priority/3`; 1 is the most urgent. A priority is a fixed amount of age added to the weight, so age wins in the end and nothing starves: level 1 is worth three times `PRIORITY_AGE` (60 minutes), three hours; level 2 two hours; level 3 one; no label nothing. Every board reads it with the open tickets (`Board::open_tickets`). A ticket with a priority label that names no level (`priority/high`), or with more than one, has none, and the tick names it in a warning on stderr (`zaf <project>: warning: #5: its priority labels are ignored: the label `priority/high` is not priority/1, priority/2 or priority/3`), never a failure. zaf never writes, sets or removes a priority label: it is the Engineer's input, not a state label, and the label sync leaves it alone.

**What a tick prints.** The text output of a real tick (not `--json`, which keeps its fields) is a short block, each line left out when it has nothing to say: `tick 14:32` (local time); what the tick did (`unblocked`, `labelled`, `ran`, `started`, `wait`, `question on`, `asked #61 on #7: <cause>` for each question with its cause, and `launching` for a planning or challenger instance); `running  challenger instance 2 on #4, 6 min` for each live instance and each live task phase (`running  implement #3 (epic #1), 4 min`), read as `zaf status` reads them; what it passed over, as the dry run words it (`#4 skipped: the challenger runs on it`), and each ticket its epic or a question holds, from the placement (`#3 skipped: its epic #1 is not challenged yet`); what waits on the Engineer (`waiting on you: 3 questions (#29 #30 #31)`, `waiting on you: epic #1 is not signed`); and `nothing to do` when none of those has a line, never the bare word `idle`. A read that fails prints `could not read <what>: <why>` and the tick's result stands. A tick the scheduler runs names who asked for it on the line under `tick 14:32` (`asked by: phase-end implement #7, ruling #45`, the first eight and then `and 3 more`; `asked_by` with `--json`) and ends with `next tick 14:37`, when the timer asks next; one that cannot read the facts says `could not read the facts: <why>; kept the placement of 14:27 and started no phase`. With `--no-wait` and no scheduler, a tick skipped for a held `spawn.lock` prints `tick 14:32 skipped: another tick holds spawn.lock`; the scheduler, whose tick waits for the lock instead, prints that line once with `; it runs once the lock is free`. The `post-tick` input is unchanged. After the slots line, before what the tick did, come where the tickets sit, from the trace below: one line for each ticket whose place differs from the trace's last line (`#7 lane(implement) -> running(implement)`, `#9 new -> lane(brief)`, `#5 done -> gone`), then one count line (`26 tickets: 1 running, 3 in the lane, 8 waiting, 14 done`, with `, 2 not read` for tickets the core could not read), whose `done` adds the done tasks of the open epics, read from the epics' task lists, to the tickets the core placed as done; with `--more`, every ticket instead, one line each, a moved one as its move (`#8 waiting(ticket #7)`). A tick with no ticket to place prints neither, and these lines are no act: they never stand in for `nothing to do`. `--json` carries the same `moved` and `tickets`.

**The trace (R24).** Every real tick appends one line of JSON to `.zaf/ticks.jsonl`, so the Engineer can check where everything was; the dry run writes none, and zaf never reads the file back to decide anything. The line is written once the phase steps have run and before the planning and challenger launches do. Its keys: `at`, when the tick began (RFC 3339, UTC), and `zaf`, the version that wrote it; `tickets`, every open ticket with a phase list where the core (§5.2) places it before the tick acts, as the dry run's `placement` shows it (running with its phase, head and start; waiting on each thing in the core's order: epic, question, ticket, check with its head; in the lane with its next run, since when and its weight in seconds; done), each with its `short` place (`running(implement)`, `waiting(question #45, ticket #5)`, `waiting(check a1b2c3d)`, `waiting(epic #1)`, `lane(implement)`, `done`), and `unreadable`, the tickets it could not read; `did`, what the tick did (the model phase started, the waits launched, the `zaf` actions run with their exit codes, the questions raised, each with the issue it was raised on, the question and its cause (`{"task": 7, "question": 61, "cause": "…"}`; a line written before causes were kept lists the issue alone, and still reads), the tasks unblocked and released, the other labels set (`relabelled`, each with `task`, `from`, `to` and `why`, left out when none), the planning and challenger instances launched, the launches found lost); `skipped`, what it held back, as its block words it; and `moved`, each ticket whose `short` differs from the last line that had tickets, with `from` (null for a new ticket) and `to` (null for one gone). The placement written is the one the phase steps acted on, gathered once. A tick that stops before it places the tickets (a failing `pre-tick` hook, a board or a forge that fails) still writes its line, with an `error` in place of `tickets` and no move. A tick drops the lines older than 14 days as it writes, writing the file whole under a name of its own and renaming it into place; otherwise it appends. It holds `.zaf/ticks.lock` for the few milliseconds of reading and writing the file, since `spawn.lock` is held only while a tick plans and two ticks may overlap. A trace that cannot be read or written is one warning on stderr, and the tick's exit code is its own. `.zaf/.gitignore`'s allow-list keeps both files out of git.

`zaf spawn trace [<ticket>] [--since <when>]` prints the moves, oldest first, one line each with the local time of its tick (`17:15 #7 lane(implement) -> running(implement)`), and a date line where the listing crosses a day. A ticket keeps that ticket's moves; `--since` takes an RFC 3339 time or a span back from now (`2h`, `3d`); `--more` adds what each tick did under its moves, worded as the block words it; `--json` prints `{"moves": [{"at", "ticket", "from", "to"}]}`, with `did` under `--more`. It only reads and takes no lock, so it never holds up a tick and needs no scheduler running. No trace yet says so and exits 0, and so does a filter that keeps no move (`no moves of #9`); a malformed `--since` exits 2, and a trace that cannot be read exits 2.

**The scheduler.** `zaf spawn --watch --version <v>` is the project's scheduler, a process that stays up in the foreground and the only thing that ticks while it runs; its ticks are the ticks above, one at a time and never two at once. It holds `.zaf/scheduler.lock` with `flock` for as long as it runs and writes one line in it naming itself: `{"pid":4242,"start":"123456","since":"2026-11-13T08:02:06Z","zaf":"0.3.1","version":"0.4.0"}`, its process, the start time the system gives it, since when it runs, the zaf it runs and its `--version`. A second `zaf spawn --watch` says where the first is (`a scheduler already runs here: pid 4242, since 2026-11-13T08:02:06Z (zaf 0.3.1, --version 0.4.0)`) and exits 1. A line left by a scheduler that died is taken over, and the new one says so (`scheduler up, taking scheduler.lock over from pid 4242, which is gone: …`). Who runs is decided by the lock, not the line: a reader (the asks below, the hub) tries a shared `flock` on the file without waiting, and a scheduler runs only while that is refused; the line then says where it is, the process it names checked live. A lock nobody holds is no scheduler, whatever its line still names. A reader holds its shared lock for an instant and never waits; a scheduler that starts tries again past one, and rewrites its line in place, so a reader never reads half of it. `spawn.lock` stays the short lock of a tick's reads and writes.

A tick is asked for, not waited for. An event that changes what a tick reads appends one line to `.zaf/tick.request`, when it was asked and who asked: `2026-11-13T08:02:09Z phase-end implement #7`. The askers are the launcher once a phase has ended (`phase-end <action> <task>`), `zaf board ruling` (`ruling #45`), `zaf board question` (`question on #7`), `zaf epic sign` (`sign #1`), every other verb the hub reports (`claimed #7`, `merged #7`), and `zaf spawn --once` (`zaf spawn --once`). With no scheduler running nothing is written and the verb works as before. The scheduler looks at the file's size and modified time each second, as the hub does with its reports, and runs one tick for every request that came since its last tick began, its block naming them all once; the file is emptied once it passes 16 KiB, under its own lock, and nothing in it is lost; one that cannot be emptied keeps what was read, served, and is named on stderr each time it fails. A request that cannot be written asks for no tick, and the scheduler's timer still does: `zaf spawn --once` says so and exits 2 (`the running scheduler (pid 4242, since …) was not asked for a tick: <why>; no tick was asked for`), the launcher writes the same line in the run folder's `post-phase.log`, and the other askers, their own work done, keep their exit and say so in one line on stderr that ends with the timer (`zaf board ruling: the running scheduler (pid 4242, since …) was not asked for a tick for ruling #45: <why>; its timer picks the change up at its next tick`): the ruling stays recorded, the epic signed. The timer asks too, `[spawn] tick_minutes` after the last tick ended, whoever asked for that one. A tick that waits for `spawn.lock` keeps its requests until it runs.

`zaf spawn --once` asks the running scheduler for a tick and exits 0 with one line, `asked the running scheduler for a tick: pid 4242, since …` (`{"asked": {"pid", "since", "zaf", "version"}}` with `--json`), so no tick runs beside the scheduler's; with none running it ticks as before, and `--no-wait` keeps its meaning. With another `--version` than the scheduler's it is refused with exit 1, naming the scheduler and its `--version` (`the running scheduler (pid 4242, since … --version 0.4.0) builds another milestone than --version 0.5.0; no tick was asked for or run: …`), since the scheduler's tick would build its own; nothing is asked and nothing runs. `--once --dry-run` always computes and prints here, and writes nothing. The launcher's ask once a phase ends is the same: a request while a scheduler runs, else `zaf spawn --once --no-wait`, as before.

What the scheduler keeps between ticks is a cache, never a source: the placement the last tick that read the facts acted on, and when it gathered them, each rebuilt from the facts the next tick gathers. Each tick reads everything again and the facts win. A tick that cannot read them (the board, the forge or the run folders fail) keeps the last placement, starts no phase, says so in its block and in its trace line's `error` (`…; kept the placement of 2026-11-13T08:01:31Z and started no phase`), and the loop goes on; so does it after a tick that fails (`tick 2 failed with exit 2; the watch goes on`).

The scheduler is never stale. It remembers the path it was started from and the identity of the image it runs (device, inode, size and modified time, read from the running image), and at the top of its loop, between two ticks and with no request waiting for its tick, never during a tick nor while a planning or challenger launch runs, it looks at the path. A file that changed, and is the same at two looks in a row, is run as `<path> --version`: exit 0 within ten seconds, and the scheduler says `restarting as zaf 0.3.2` and `exec`s it with the same arguments, the same process with the same pid and start, which takes the lock again (`scheduler restarted from zaf 0.3.1: pid 4242, since …`, `since` kept) and ticks at once (`asked by: restart`). A file that does not answer is named on stderr (`the new binary at <path> does not run (its --version ended with exit 3); this image goes on, and tries again once the file changes`) and the old image goes on until the file changes again. The requests it served are dropped from the file first, so the new image names only those no tick has served. SIGINT and SIGTERM are held back from its last look for one until the new image catches them, so a stop that lands during the restart stops the new image (or this one, when the restart failed). Every zaf it starts again, the restart, a tick's `zaf spawn phase` and the launcher's `zaf do` and tick among them, is started from the path it was started from, never from the ` (deleted)` name the system gives an image whose file was replaced.

SIGINT and SIGTERM end it between two ticks, or once the tick that runs has ended: it never kills a phase, which runs as its own process. They are caught before anything is taken from the request file. A Ctrl-C in its terminal reaches the scheduler alone: every process a tick starts (`gh`, `curl`, `jj`, `zaf spawn phase`, the hooks, the inline actions and the launches) runs in a process group of its own, so the tick runs to its end with its reads whole, and nothing it started is killed. It clears its line, lets the lock go, says `scheduler stopped on SIGTERM; scheduler.lock released` and exits 0; requests no tick served stay in the file for the next scheduler, which names them in its first tick. There is no stop verb. The hub shows the scheduler from its lock (`watch`: `running`, `pid`, `since`, `zaf`, `version`) and when the last tick began from the trace's last line (`last_tick`). One scheduler for each project; one for the machine is later.

The model the tick starts runs as its own process, so phases of different tasks run at the same time, as many as the budget holds, and phases of one task never overlap (ruling 19). The `zaf`-kind and `wait` actions are not the tick's one start (ruling 22). Planning and the challenger are charged XS and a release E, though the tick does not launch a release yet; the release instance's launch, the zaf service (#353) and the split of `zaf slice`, `zaf check` and `zaf ask` into a decision and an action (#422) are not in this epic.

The budget is that of #419: a number of units for the machine, an absolute cost for each size, a table for each project, and live use read from the process table. The units are `[spawn] budget`, a positive integer set only in the zaf home's `config.toml`; unset, there is no machine cap. The costs are `[spawn.sizes]`, with the keys XS, S, M, L and XL (1, 2, 4, 8 and 16 by default), which a project may override; E has no key. A launch fits when the project runs fewer instances than its `[spawn] slots` and the live use plus the size's cost stays inside the budget, and `zaf status` shows the units in use against it. The live use, and the rule that one E runs at a time, count every live process that carries `ZAF_RUN`, from any project: a process that outlived its run (an orphaned grandchild of a run that recorded its exit, or whose own process is gone) still uses memory, and one of size E still holds the one E. Such an orphan holds no slot, since the slots come from the run folders, and `zaf status` does not show it as an instance. It is charged for a phase only while the phase runs, so a task waiting on review or CI holds nothing, and each phase must fit again, at the task's size, when its turn comes (ruling 14). After 30 minutes a passed item holds the budget for itself, the starvation rule of #419, read from the forge and never counted or stored. E costs the budget minus a reserve, so one E runs at a time and small work keeps running beside it; the reserve is configurable and defaults to 6 units (ruling 24). A resumed phase's brief holds only what that phase needs, which zaf builds from the task, the pull request's diff and the new findings (the review comments or the CI failure); the exiting model may leave one hand-off comment on the pull request, and zaf includes it (rulings 3 and 15).

**Hooks.** A hook is an action in a `hooks` folder inside an actions folder, `.zaf/actions/hooks/` in a project and `~/.zaf/actions/hooks/` on a machine, and the project's wins as an action does. It is named after its event, one file for each, and there are three events (rulings 9, 10 and 13). A hook cannot be run as a normal action: `zaf do hooks/pre-tick` is `NOT_RUN`, exit 125, and `zaf do` lists none. The hook's file carries the metadata of §3, and `zaf doctor` names a file whose name is no event.

| Event | Runs | Gets | A failure |
|---|---|---|---|
| `pre-tick` | before each tick | nothing | fails the tick; a hook that fails and does not care returns 0 after its own error handling (ruling 11) |
| `post-tick` | after every tick, idle ones included | the tick's outcome as JSON on stdin: the model started (task, phase action, units) or none, the waits launched, the `zaf` actions run with their exit codes, the questions raised (`questions`, the issues, and `asked`, each with its question and cause), or that nothing was ready; no exit code of the model, because the tick never waits (ruling 12) | reported, and changes nothing |
| `post-phase` | when a phase's process exits, run by the launcher that started it | the task, the phase action and the process's exit code, as JSON on stdin (ruling 21) | logged, and changes nothing |

**Triggers.** A tick runs in at least three cases (rulings 25 and 26). Every five minutes: the scheduler, `zaf spawn --watch`, ticks at once when it starts and then whenever the timer asks, `[spawn] tick_minutes` minutes (five by default, in any project manifest layer) after its last tick ended, until it is stopped; a tick that fails is logged and the loop goes on, and zaf writes no system timer; the zaf service (#353) replaces it later (the ruling on #428). Every time a phase ends: a task completing is its last phase ending, so the one event covers both, and the launcher that runs `post-phase` then asks for a tick, so freed budget is reused at once: a request in `.zaf/tick.request` while a scheduler runs, which ticks within a second or two, else `zaf spawn --once --no-wait`, which does nothing and exits 0 when another tick holds `spawn.lock`, since that tick reads the same forge; plain `--once` still waits, and `zaf spawn` with neither flag still refuses. The other events that change what a tick reads ask the same way (above). A webhook is the third trigger, for waits that end outside zaf: when a review is posted or CI finishes, the forge's webhook asks for a tick at once through the same entry point. A webhook carries no state, because the tick still reads everything from the forge, so a missed one costs at most five minutes, and a wait that ends outside zaf has no process to exit and is found by the five-minute tick. The listener is the zaf service (#353), not this epic.

### 5.2 The scheduling core

The scheduler rebuild ruled on 2026-11-12 (rulings R12 to R22 of the scheduler notes) starts with its pure core, `domain::schedule` (`zaf/src/domain/schedule.rs`): functions that place every ticket from facts alone and work out what a run meant. It reads no file, forge, clock or process table, and writes nothing. The tick and `zaf spawn phase` decide every start from its placement, through one gate (§5.1, "Where a ticket sits" and "One gate for both paths"), and the getting-nowhere count is its `nowhere`. `zaf spawn --once --dry-run --json` carries `placement`, every open ticket with a phase list (`Board::open_tickets`: the open tasks not `done`, whatever their state label, in number order) placed as running with its phase, waiting with each thing it waits on, in the lane with its next run, since when and its weight, or done, and the tickets that could not be read; every real tick writes the same placement to its trace line (§5.1), and the plain-text dry run reads nothing for it.

**Where a ticket sits.** In exactly one place, the first that holds: running, when a phase run of it is live; done, when its pull request is merged or every phase's end fact holds; waiting, when its epic is unsigned or unchallenged, a question is open on it or its epic, a dependency is not done, the checks at its head have not all ended (none registered counts as not ended), or its current phase awaits the outside, listed under every one of these that holds; otherwise in the lane, with its next run (the current phase, or its `on-fail` when the phase failed on something the `on-fail` answers) and since when. The current phase is the first whose end fact does not hold at the pull request's head: `pr-open` needs a pull request that changes a file, and `exit` a run of the phase that exited 0: for a phase listed after the one that carries `pr-open`, a run that left the head and raised no question; for one listed at or before it (a brief, an implement that opens the pull request), any run that raised no question, whatever the head, so a fix pushed later does not reopen it. A run that raised a question is never done by its exit code, open or ruled: once ruled, the phase runs again. A list with no `pr-open` phase keys every `exit` on the head. State labels are its output only, never read back.

**What a run meant.** Worked out from the run's report and the facts, in this order: a question the run raised that is still open is a wait on it, whatever the exit code; the phase's end fact holding at the current head is done; something outside that has not ended (the checks at the head, or a review, CI or merge the phase awaits after exiting 0) is a wait on the check; anything else failed. A phase is getting nowhere after three ended runs of the same action that began and ended at one head, counted after the last ruled question's marker, exit 0 included; no exit code, exit 125 and exit 128 or above never count.

**Weight and the waits that ask.** A lane entry's weight is its age since `since` plus its priority's worth (`lane.rs`: level `n` is worth `4 - n` times `PRIORITY_AGE`), computed each tick and never stored. `wait.rs` finds, as facts, the waits that must not last without the Engineer hearing of them: a check wait past `CHECK_DEADLINE` and what it still awaits (no check, the pending ones, or what the phase awaits from outside), a dependency that can never complete, and an epic planned and not challenged past `CHALLENGE_DEADLINE`; a ticket that also waits on a question or on its epic has no clock. Raising the question is the tick's (§5.1, **The questions**).

## 6. The manifest

```toml
[actions]        timeout_minutes = 30                      # optional; absent = 30
[check.pr]       steps = ["ci"]                            # or action steps: ["ci", "action:nodes-check"]
[gate]           light = "zaf do gate-light"               # or a literal line, as today
```

The actions folder is not configurable: `.zaf/actions/` in a project, `actions/` in the global home. The scheduler of §5.1 adds a `[phases]` table, one list of action names for each task type, and `[spawn] tick_minutes`, the minutes the scheduler (`zaf spawn --watch`) lets pass after a tick before its timer asks for the next (five by default); the machine budget and the reserve are `[spawn]` settings in the zaf home, as #419 rules. `[spawn] budget` is read only from the zaf home's `config.toml`: set in `.zaf.toml` or `.zaf/config.toml` it fails the load, naming the file. `[spawn.sizes]` may sit in any layer, the zaf home's below the project's, and takes only the keys XS, S, M, L and XL; any other key, `E` among them, fails the load, naming it.

## 8. Rulings

Rulings 1 to 19 are of 2026-11-03; 20 to 30 of 2026-11-04.

1. **Global home:** a configurable zaf home, default `~/.zaf/`, laid out like a project; `zaf setup` makes it first when it has not run, and may be called from the beginning.
2. **Local home:** projects gain a committed `.zaf/` folder; actions live in `.zaf/actions/`; the file name is the action name, no spaces, hyphens and the like allowed.
3. **Manifest:** `.zaf.toml` at the project root or `.zaf/config.toml`; both may exist and combine, `.zaf.toml` winning on a conflicting property.
4. **Verb:** `zaf do`.
5. **Output:** the log is `.zaf/logs/<DATETIME>_<ZAF_ACTION_NAME>.log`.
6. **Ignore rule:** zaf writes `.zaf/.gitignore` for the machine state.
7. **Actions are the "make it yours" layer, and zaf is the abstraction layer over them:** `zaf do push` may do far more than a push.
8. **Contract:** an action returns 0 for success and non-zero for failure (1 canonical).
9. **Composable:** an action's body may run `zaf do something_1; zaf do something_2`.
10. **Two parts:** metadata (the description and what each non-zero return value means) and the body.
11. **Hand-back (#121):** the last non-empty line of the action's log is its value; `merge-base` exit 1 is conflicted; other non-zero is a backend failure.
12. **Modes and slices (#122):** actions are callable by anybody by default, not every action by everybody: a mode like a file's, owner the Engineer, group the roles named, others the rest, bits r w x, default `755`, the caller's role passed through nesting. The slice family is action language, `zaf do slice-*`, the merge conditions inside `slice-merge`.
13. **Sequencing (#123):** 0.1.3 is folded into 0.2.0: #99's tasks move under #103, one release on `feature/0.2.0`, #94 re-scoped against #105.
14. **Calling past an override (#124):** was a flag that called the shipped action past an override; with no built-ins (16) it is `--tier machine`.
15. **Moving the manifest (#125):** only an explicit `zaf setup` moves a root `ZAF.toml` to `.zaf.toml`; other verbs read it, warn, and make the homes non-destructively.
16. **Overridable, never wider (#127):** landing steps declare `750` group team, release; a shadowing file never widens the run bits of what it shadows.
17. **No shipped actions (#128):** zaf ships none; whoever set zaf up writes them; two tiers; the ways repo writes its own set, isolated from Zurfur's.
18. **Team Phases (#129):** an action's metadata names the phases it may run in; zaf derives a task's phase from the board and its records, never the environment; phases are the guard that holds, modes guard against mistakes.
19. **Merge conditions (#130):** enforced through phases: `slice-merge` runs in `land`, which needs a clean `zaf check pr` on the PR's current head; no result is not clean.
20. **Slice records (#134):** zaf writes them from the hand-back of `slice-open` and `slice-pr` on exit 0 and forgets them on `slice-merge` and `slice-drop`; `check` and `changes` read the workspace from them.
21. **Merging outside `land` (#135):** `[forbidden]` denies `gh pr merge`, `zaf do pr-merge` and `zaf do land` for instances; they merge through `slice-merge`, and the release instance through the `release` action. The depth guard was rejected because it keys on the environment (principle 8), and leaving the hole was rejected because the forge protects only `main`.
22. **Marking done (#136):** `zaf board done <task>`, refused unless the task is in `land` or its recorded pull request has merged.
23. **A slice action's slice (#137):** a `target: task` run gets `ZAF_SLICE`, `ZAF_PR` and `ZAF_TASK_TITLE`; `[env]` cannot set them.
24. **Result words and `NOT_RUN` (#138):** exit codes stay numbers, because the OS carries only an integer and a script branches on it, and what zaf prints gains words, because a model reads words. A body that never ran is `NOT_RUN`, exit 125, reserved. Verbs keep `0`, `1` and `2`.
25. **`land` needs the workspace at the PR head (planning decision 1):** a workspace ahead of the PR head is not `land`, otherwise `slice-merge`'s `push` merges commits nobody reviewed.
26. **A failed task check stays in `build` (planning decision 2):** only a clean one moves the task to `check`, so no pull request opens on red and `slice-drop` still works.
27. **Drop and reopen (planning decision 4):** `slice-open` is refused past `claim`; forgetting a slice also removes the task's check records; `slice-drop` also runs in `check`.
28. **Accepted as planned:** `slice-merge` on a done task refuses (decision 3); a base merge pushed by `slice-merge` followed by a failed `pr-merge` needs a new `check pr` (5); doctor finds needed names by scanning bodies for a literal `zaf do` (6); the `ZAF.toml` rename comes last (7); `ZAF_BASE` arrives in #140 (8).
29. **The ledger (#147):** zaf holds an SQLite ledger. It is zaf's own state, not a committed file, so no row has to reach `main` and the release has no step for it.
30. **Logs are kept (#158):** a check step's whole output goes to `.zaf/logs/<DATETIME>_<name>.log`, git-ignored, as an action's does (§3). What the step returns is short: a word and the log's path.
31. **Tickets state scope, not files:** a ticket's `Owned paths` becomes `Scope`, the capability it changes in words, with a file or folder named only as a place to start, and `Out of scope`, what it leaves alone and the ticket that has it. The programmer goes where the goal needs and stops at `Out of scope`. `Architecture` goes: `zaf check` takes its symbols from `Interfaces` and looks for them in the whole tree. The reason: 5 of the 8 questions raised during this build came from a closed file list (#149, #157, #158, #166, #173), and each one stops the loop for the Engineer. Tickets written for people state scope as behaviour with explicit exclusions; agent vendors treat a named file as a hint; no measurement supports a closed list.
32. **One behaviour per ticket:** the Goal is one sentence with no "and". Size S expects a pull request under 200 lines and M under 400; anything larger splits. These are planning targets read against the merged pull request, not gates. The numbers come from review research on people and are unproven for agents.
33. **Batch two, limit 45:** `[roles.team] batch = 2`, which matches the two programmers an instance runs at once. The runner limit stays 45 minutes: instances are short-lived by design, so one that reaches the limit is carrying too much work.
34. **Phases and modes, from the build (#234 to #238):** a failed task check with a `.pr` record and no result for the current head is `build`. A mode refusing the owner prints `the Engineer`. A blank `ZAF_INSTANCE` does not parse, so it is refused; `zaf setup` keeps treating blank as none. There is no fixed list of roles: the role a well-formed `ZAF_INSTANCE` names is the caller's and `group` decides its digit, so a project's own role works without a zaf release.
35. **`zaf hub` (the Engineer, 2026-11-04):** the live view of §5 is in 0.2.0, so it is there for the first real dogfood. No tail: it redraws when a report arrives. A bar for each epic, each group and each model's ticket, and a general word for what the model is doing. Groups are `group:<name>` labels, set from the re-plan's map; the planning instance labels what it files, and Unit of Work (#232) can build on them later.
36. **Shadowing, from the build (#264):** a project file shadowing a machine file with invalid metadata is refused, `NOT_RUN` naming both, since the machine file's write bit cannot be read. A refused shadow is refused for running only; `--show` and the listing still show the file, which is how the Engineer sees why. A run of a shadowing file needs both files to permit the caller, each under its own group, because masking digits would let a longer `group` widen it.
37. **The design source (#266):** `[design]` is `repo-dir` on `docs/`, and `docs/index.md` lists `zaf-actions.md` as page `zaf` and `zuri-ai-framework.md` as page `zuri`. With no source `zaf ask` rejects every citation, so all 52 answers up to this ruling were `not settled` with no page cited. Tickets keep naming docs by path, so `brief` stays small and programmers get the design through `zaf ask`.
38. **The release role and slice records, from the build (#272, #273):** the ways manifest has a `[roles.release]` table (opus, xhigh, profile `build`, 200 turns) so `release` can stay in §7's groups; the spawner does not launch it yet. A slice record's workspace is an absolute path to an existing directory, a symlink to a directory passes, and it need not be inside the project. A PR number is ASCII digits above 0 fitting u64: `#12`, padded values and `0` are refused, and `007` is stored as `7`. A missing or malformed task is `FAIL`, exit 2, and writes nothing; `#140` and `140` are the same record. A slice name exiting 0 outside a project is `FAIL`, exit 2.
39. **CI is the only gate (the Engineer, 2026-11-05):** only CI stands between a task's pull request and its merge. The team instance does not run `zaf check <task>` again after the programmer's round, and `[check.pr]` is `["ci"]`, with no per-PR model review. Reviews are paid once per release, x.y.z, on the integration branch's pull request. That review covers the merge-path tickets that were security-flagged (#132, #139, #203, #204, #217, #218, #269). The programmer still ends its round on a clean `zaf check <task>`. `slice-pr` runs from `build`, and `slice-merge` drops `gate-light` (§7). The reason: the 23 tasks merged that day averaged about 80 lines of code each, at a median 9 minutes from claim to merge, and most of that was fixed cost.
40. **Units of work (the Engineer, 2026-11-05):** the rest of 0.2.0 is grouped into units of 2 or 3 tickets. Each unit has one programmer, one workspace and one pull request. Units are chosen so they depend little on each other, and so the work within one is similar. zaf has no unit yet, so each unit is one ticket that folds the others, and the folded tickets are closed pointing at it. `[roles.team] batch = 1` replaces ruling 33's batch, and `[roles.programmer] turns = 150` gives a unit room, so an instance carries one unit and stays inside 45 minutes. The four lanes (`[spawn] slots = 4`) run four units at once. #132 and #195 to #198 move to 0.2.1, and #230 is dropped along with the team's task check. This supersedes ruling 32 for units and brings #232 forward.
41. **Phase facts (#285 to #287):** a board or forge read that fails while deriving a phase refuses the action, `NOT_RUN`. A fact that is absent, such as a pull request with no head or a missing workspace, falls to the earlier phase. A claim has no expiry, because the spawner hands back a timed-out instance's claims (#95), and §3 says `claimed` where it said `live lease`.
42. **Two rulings from the build (#214, #309):** a failed `gh pr merge` exits 1, since the other actions also put forge refusals under 1. #110's CLI wiring is within its scope. A malformed `ZAF_INSTANCE` fails `zaf brief`, and with no machine home the brief lists the project's actions only.
43. **Dashboard mode (the Engineer, 2026-11-05):** `zaf hub --port <n>` serves the hub on every interface for anyone on the LAN, GET only and with no login (amended by epic #1, 2026-11-13: reading stays GET with no login, and the controls the epic adds are keyed requests, the JSON interface of §5). The ways board is public on GitHub, so the page adds only the costs and what each model is doing. It redraws on each report through server-sent events (§5). It ships in 0.2.0 as unit U13, after U7.
44. **Models report their phases (the Engineer, 2026-11-05):** each model defines its phases when it starts and reports when its phase changes, and phases may be iterative. A phase report is what redraws the hub and the dashboard. Unlike the tool-call hook, it costs one turn per change. It ships in 0.2.0 as unit U12, and the role briefs (U10) tell each role to declare and report.
45. **The documents say what was built (#325):** the manifest is `.zaf.toml` or `.zaf/config.toml`, and a `ZAF.toml` standing alone still loads, with a warning, until `zaf setup` moves it. `[env]` refuses `ZAF_` names and `CLAUDE_CONFIG_DIR`. `pr-merge` takes `--squash`, which `release` uses. The profile allow-list gains `printenv` and gives no tool rule to a gate segment that starts with a shell or wrapper tool. §4 and §7 name each action's arguments as built, and assumption 2 lists the optional keys.
46. **Actions from the transcripts (the Engineer, 2026-11-08):** the multi-step procedures models ran by hand in this repo, mined from about 130,000 tool calls in the zaf ledger's transcripts, become ways actions (§7): `ci-wait` (checks polled, then failed logs read: about 30 runs), `ship` (describe, bookmark, push, PR, wait, squash-merge, sync: every design-document PR), `issue-file` (create, read the id, link the sub-issue, label: 58 creates by planning), `task-pr` (an issue read, then a PR search: 12 runs) and `base-up` (fetch, move or merge the integration branch, push: 4 runs). The fmt, build, clippy and test chain and `jj commit` recur too, but `gate`, `gate-light` and `commit` already are those actions.
47. **zaf derives its state on read (the Engineer, 2026-11-09, #390):** state that a live source can answer is read from it on every read, never kept in step by hand, because a persisted copy goes stale. Whether an instance runs comes from its run folder and the process table: `.zaf/runs/<slug>/pid` holds the holding process as its pid and start time, the tick's from reservation and then the instance's own, written by the runner, so killing a tick leaves a running instance its slot and its claims, and a pid the OS has handed to another process reads as dead. Slots are the instances that run. ### Rulings of #421, the phase scheduler (the Engineer, 2026-11-10)

These are cited as `#421 ruling <n>`, apart from the numbers above. §5.1 says what they build.

1. **A task is an ordered list of phases (#421 ruling 1, 2026-11-10):** zaf owns the list.
2. **A model runs to the first wait (#421 ruling 2, 2026-11-10):** it runs until the first async wait (review, CI), then exits and frees its budget. Phases with no wait between them, such as read brief and implement, stay in one model run.
3. **A fresh model for the next phase (#421 ruling 3, 2026-11-10):** zaf later starts a fresh model for the task's next phase, and its brief holds only what that phase needs.
4. **A blocked phase is passed over (#421 ruling 4, 2026-11-10):** a phase blocked on an earlier phase is passed over.
5. **The queue is derived each tick, never stored (#421 ruling 5, 2026-11-10):** zaf reads every task's current phase from the forge (PR open, review posted, CI green, merged) and runs the ready phase that has waited longest.
6. **zaf runs `ci` and `merge` alone, with no model (#421 ruling 6, 2026-11-10):** a model is started only when CI is red or the review has findings to fix.
7. **The weights are the size budget of #419 (#421 ruling 7, 2026-11-10):** absolute units per size, a table per project, live usage and a starvation rule.
8. **A phase is an action, and the tick stays in zaf (#421 ruling 8, 2026-11-10):** the tick derives each task's phase, picks, checks the budget and holds the lock. What a phase does is an action: some start a model (implement, fix review findings) and some do not (`ci`, `merge`). A task type's phase list is a list of action names.
9. **A tick has a pre hook and a post hook (#421 ruling 9, 2026-11-10):** the Engineer made this the condition for ruling 8: "Add pre and post hooks to ticks and I'll agree with you."
10. **A hook is an action in a `hooks` folder (#421 ruling 10, 2026-11-10):** inside the actions folder (`.zaf/actions/hooks/`). `zaf do` refuses to run one as a normal action.
11. **A failing pre hook fails the tick (#421 ruling 11, 2026-11-10):** "A non-zero fails the tick. A file that fails and doesn't care should return 0 after its own error handling."
12. **The post-tick hook gets the tick's outcome (#421 ruling 12, 2026-11-10):** JSON on stdin of what the tick launched (task, phase, action, units) and the no-model actions it ran, or that nothing was ready. It carries no exit code, because the tick never waits. It runs after every tick, idle ones included, and a failing one is reported and changes nothing.
13. **A hook file is named after its event (#421 ruling 13, 2026-11-10):** `hooks/pre-tick` and `hooks/post-tick`, one file per event; ruling 21 adds `hooks/post-phase`.
14. **The budget is charged per phase, only while the phase runs (#421 ruling 14, 2026-11-10):** a task waiting on review or CI holds nothing, and each phase must fit the budget again when its turn comes, at the task's size.
15. **zaf builds a resumed phase's brief (#421 ruling 15, 2026-11-10):** from the task, the PR's diff and the new findings (review comments or the CI failure). The exiting model may leave one hand-off comment on the PR, and zaf includes it.
16. **The team instance goes away (#421 ruling 16, 2026-11-10):** each phase action launches the worker it needs directly, a programmer for implement and a reviewer for review. zaf does the coordinating.
17. **Phase lists are declared in the manifest, per task type (#421 ruling 17, 2026-11-10):** a ticket's Type picks its list.
18. **`zaf slice`, `zaf check` and `zaf ask` split the same way (#421 ruling 18, 2026-11-10):** zaf decides, an action does, in a later epic (#422), not this one.
19. **A tick starts at most one model, and never waits for it (#421 ruling 19, 2026-11-10):** "a tick grabs the next item in queue and either starts it (if the budget is enough and the dependencies or prerequisites are met) or pushes it back, assigning weight or the like (such as in a scheduler in a computer)." The started phase runs as its own process, so phases of different tasks run at the same time, as many as the budget holds, and phases of one task never overlap.
20. **The weight is derived (#421 ruling 20, 2026-11-10):** it is how long the item has been ready, read from the forge. Each tick orders the items by weight, walks that order, and starts the first one that fits the budget and has its prerequisites met. The items it passes are pushed back, and their weight keeps growing, as with priority aging. Nothing about the queue is stored. After 30 minutes the starvation rule of #419 holds the budget for a passed item.
21. **`hooks/post-phase` runs when a phase's process exits (#421 ruling 21, 2026-11-10, after the simulation):** it gets the task, the phase, the action and the exit code, as JSON on stdin. The launcher that started the phase runs it, so nothing is stored to remember the launch.
22. **Actions that need no model do not count as the tick's start (#421 ruling 22, 2026-11-10):** a tick runs every ready no-model action (`merge`), at no cost to the budget, and may also start one model.
23. **Each phase action declares its kind (#421 ruling 23, 2026-11-10):** it starts a model (costs the task's size), waits on the outside (costs nothing), or is run by zaf alone (costs nothing). zaf reads the kind and guesses nothing; a review can be either a reviewer model or an outside wait, by its action.
24. **E leaves a reserve (#421 ruling 24, 2026-11-10):** E costs the budget minus a reserve, and one E runs at a time, so small work keeps running beside it. The reserve is configurable and defaults to 6 units ("The reserve is configurable. I agree on 6."). This amends #419, where E took the whole budget.
25. **A tick runs in at least two cases (#421 ruling 25, 2026-11-10):** every five minutes, and every time a phase ends ("a tick happens in two places at LEAST: every five minutes or every time a task is completed. Likewise, a phase change informs of it."). A task completing is its last phase ending, so the one event is a phase ending. The launcher that runs `hooks/post-phase` then asks for a tick, so freed budget is reused at once. A wait that ends outside zaf has no process to exit, so the five-minute tick finds it.
26. **A webhook is a third tick trigger (#421 ruling 26, 2026-11-10):** for waits that end outside zaf. When a review is posted or CI finishes, the forge's webhook asks for a tick at once ("Regarding the review or CI, that's where I wanted to introduce webhooks."). The webhook carries no state: the tick still reads everything from the forge, so a missed webhook costs at most five minutes. The listener is the zaf service (#353), not this epic; this epic ships the two triggers of ruling 25 and one entry point that asks for a tick, which the service calls.

## 10. Is it saving tokens

Raw totals cannot answer this, because they move with how much work was done. The question is whether the same work costs less than it did.

**The unit.** Estimated dollars per merged task, per epic, because dollars weight the token kinds by price. Each epic also shows tokens by kind, turns per task and context at turn one and at the end. The figure to compare is the median by size (S, M), since one large task skews a mean. Everything the epic cost counts: planning and re-plans, team instances, programmers and keepers.

**The verb.** `zaf report --epics` prints one row per epic with its share per role, from the ledger, a subagent counted through its parent session, and the tasks done from the board. It also prints one line for what ran outside any epic, because that spend is invisible otherwise. This is the tokens-per-role table the framework's verb list promises and `zaf report` does not yet print.

**The ledger.** Transcripts expire (30 days by default), so zaf holds the numbers itself: an SQLite database at `~/.zaf/ledger.db`, one row per run, with its project, role, epic, tasks, model, turns, tokens by kind, context at turn one and at the end, and times. `zaf report` and each `zaf spawn` tick ingest the transcripts they find, updating a run while its transcript still grows, and a row outlives its transcript. Dollars are computed on reading, so a price change cannot look like a saving. The ledger is machine state, never committed, so a rebuilt machine starts empty unless it is backed up.

**Reading it.** An epic saved tokens when its median per size is lower than the last epic's on at least five tasks of that size; with fewer, the row says `too few`, not a verdict. Different work still differs, so a change that claims a large saving gets a benchmark: one old task re-run from its parent commit under the current pack, the only direct comparison, at the cost of that run.
