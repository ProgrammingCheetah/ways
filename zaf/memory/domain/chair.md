# The captain's chair

Bare `zaf` on a terminal opens the chair (release 0.5.3): one full-screen view of the machine's projects, a tab each, from which the Engineer answers questions without leaving zaf. The design is `.teams/releases/0.5.3/design.md` (D1 to D15); this note says how the built core is laid out.

## Observations

- [layout] `app::chair` is the read model: `ChairState` per project, built from the hub's `ProjectState` and `next_for_project`, every string made printable; the gatherer thread and the pending queue live there too #layers
- [layout] `src/cli/chair/` is the terminal adapter and the only place that names ratatui, crossterm, portable-pty, tui-term or vt100; `tests/architecture.rs` checks it #layers
- [rule] The chair is a pure state machine (`cli/chair/model.rs`): keys in, commands out; the runtime (`run.rs`) carries the commands out, so the key flows are unit tests #testing
- [rule] One read model with the hub's page: orphaned claims, each ticket's waits and the releases due are in `ProjectState` itself, never read twice through `zaf status` #determinism
- [rule] The draw loop never reads a port: a gatherer thread per tab, the shown tab every 5 s, the rest every 60 s, at once after a report or a write #responsiveness
- [rule] A GitHub board's tab (either kind) has a 20 s floor (`gatherer::floor_of`, read from the manifest when the gatherer starts): no read starts sooner than 20 s after the last one started, whatever asked (cadence, report, write); asks inside the floor are one read at its end. Forgejo has none, so D3's 5 s and 60 s stand #responsiveness
- [rule] A ruling waits 5 s in `PendingQueue` before it is written through `zaf board ruling`'s app path; quitting writes what waits first #undo
- [extension] Each pane is a stateless `Pane` (`cli/chair/panes.rs`); each feature fills its own files: the epic views and the tree in `panes/detail/` (F6), why and Live (F7), the phase pane (F8) #stubs
- [extension] The palette is a registry by feature (`cli/chair/palette.rs`): an entry only presses a key (`Run::In` focuses a pane first), so a feature adds its entry to its own section and its handler where the key lands; F8's `o` and `^w c` land in `model/phase.rs` #palette
- [rule] A read a key asks for (an epic's body and its release's documents, a ticket's reports and log tail) is a `Look` and comes back as `Update::Looked`: an epic is a job on the tab's gatherer thread (`Gatherer::run`, D3), so it waits for the read under way (about 25 s for ways on Forgejo), a ticket's files are read on a thread of their own; `Chair.looks` keeps it while the screen still asks for it, and Live's ticket is read again with every fresh read of its project #responsiveness
- [rule] Nothing in the chair asks where a ticket sits: why and the tree use the square's waits, phase and phases done that `ProjectState` already carries; `place`, `current_phase` and `phase_status` stay forbidden outside the core #determinism
- [rule] The status fields (slots, guard, unparsed tasks, blocker cycles, dead blockers, the next version) are `ProjectState.status`, filled by the same gather as the rest; a ticket's time and tokens are `LineTask.cost`, from the ledger already read for the hub #determinism
- [rule] Signing an epic waits 5 s in `PendingQueue` like a ruling (`ChairAction::Sign`) and goes through `app::epic::sign` with the instance guard; it shows as signing until a read shows the epic signed #undo
- [rule] With no release due, the inbox offers to begin the next version; the offer has `begins` set, waits on no one (`ChairState::waiting`, the badge and the pings skip it) and runs nothing from the inbox #inbox
- [gotcha] A phase run's log is found from its run folder: the log its `output` names, else `.zaf/logs/<stamp>_<action>.log` (and `.2.log`…) for the second the `task` file was written and a few around it, the one naming the ticket first; a `claude -p` phase writes its log only at its end, so Live says "working" #logs
- [gotcha] Now's limits line comes last, so at 80×24 with a release due it gives its row to the scheduler and its keys #layout
- [rule] The build controls (F9, F15) never use the hub's in-process watch, which ends with its process: `b` spawns `zaf spawn --watch --version <v>` detached (`setsid` in `pre_exec`, stdin `/dev/null`, log `.zaf/logs/<stamp>_spawn-watch-<v>.log`, every `ZAF_` variable but `ZAF_HOME` dropped), `<v>` the one version whose epics are signed and open, asked by digit when there are several #build
- [rule] `B` sends SIGTERM only to the scheduler whose pid the Engineer was asked about (`WatchView.pid`, read again from the lock when it runs); a lock that changed meanwhile is refused and nothing is sent. `x` stops through `spawn_stop::stop_in`, `t` writes a tick request (`request::ask`), never a tick of its own #build
- [rule] Every control asks on the status line first (`Mode::Ask`): starts and ticks `[Y/n]`, stops `[y/N]`, Enter takes the capital; `q` is no answer there and `Ctrl-C` quits #undo
- [rule] Controls run behind the `build::Controls` port, one thread each; `Machine<P: Processes>` takes the lock read, the signal and the detached start from `P`, so their logic is tested against a fake #testing
- [rule] Pings (F10) are new by id against the tab's previous read: the issue number, the kind for ready work no scheduler ticks (its title counts), the title for the rest; the first read, a read without the board and the read after it ping nothing. One bell per read, at most three notifications; a version whose epics all become done notifies too #pings
- [rule] Desktop notifications pass the text as arguments only: `notify-send --app-name=zaf -- <title> <text>`, `osascript` with a fixed `on run argv` script; `ZAF_NOTIFY=0` turns them off. notify-send reads the text as markup, so `& < >` go as entities; titles are cut to 80 characters, texts to 300 #safety
- [gotcha] Enter on ready work no scheduler ticks is `b`: the inbox pane ignores that Enter and the chair's keys-from-anywhere take it, since starting needs the project's state #keys
- [gotcha] To see the chair on real data without tmux or pyte: a python `pty.fork` driver and a small reader for cursor moves; keep a CSI split across reads whole, and remember `os.kill(pid, 0)` succeeds on a zombie #testing
- [layout] The phase pane (F8) is three parts: `panes/phase.rs` is pure (the `Session` as the chair sees it, `PhaseCommand` out, `PhaseEvent` back, key routing, the `Ending` timer, the pane drawn with tui-term), `model/phase.rs` is the chair's moves on it, and `session.rs` is the runtime: the pty, a reader and a worker thread, and the one chair module that calls begin, the release folder and the runner, behind `PhasePorts` so a test fakes the board and the run #phase
- [rule] The runner's third stdio plan, `OnPty(PtySide)`, takes the pty's side as a plain fd, so the app layer names no pty crate; the body runs `setsid` and `TIOCSCTTY` in `pre_exec`, leading its own session with the pty as its controlling terminal, and the hang-up and kill go to the pty's foreground group (`tcgetpgrp`), never the chair's own #phase
- [rule] `ZAF_READY` (`.zaf/begin/<version>/<phase>.<token>.ready`, the token random per session) is set only by the chair; `zaf begin ready` makes it with `O_EXCL|O_NOFOLLOW` (never through a link) and is refused with 1 when it is unset, so a plain `zaf begin` session is told to end with `/exit`. Only a regular file counts as ready (`begin::is_ready`). The ready file or exit 0 leads to `complete_phase`, whatever the code (`begin::leads_to_sign`); the file is removed once the signature is settled, and the signed document is written beside its real file (links followed) and renamed #phase
- [rule] Once ready the chair clears Claude's input (Ctrl-L, Claude Code's `chat:clearInput`, then Ctrl-U), types `/exit`, Enter 400 ms later, each key in a write of its own, hangs up at 5 s and kills at 10 s; `Ctrl-w c` (and the palette's entry) leaves from any pane, asking `[y/N]` when not ready; `q` and `Ctrl-C` ask while the action runs; `Sign it? [Y/n]` is answered through `complete_phase`'s ask, carried on a channel to the worker thread; signed objectives set `follow`, which selects the design item on the next read #phase
- [rule] The phase questions live in the `Session`, not in `Mode::Ask`: a control's yes runs a `Control` through the build port, a phase answer types into the pty or answers the worker; they share the look (`Status::Phase`, `panes::phase::spans`) #phase
- [gotcha] Spike of 2026-11-19 (claude 2.1.328): `/exit` ends Claude Code with 0 in under a second; Claude's Bash tool passes `ZAF_READY`; Claude asks the terminal for DA1, the kitty keyboard and OSC 7501 and works without answers, and uses the alternate screen, synchronized output, mouse modes and bracketed paste. tui-term 0.3.4 matches ratatui 0.30; portable-pty 0.9.0 builds on linux-gnu (musl and macOS left to CI) #phase
- [gotcha] portable-pty does not hand out the slave fd: the chair opens `tty_name()` itself with `O_NOCTTY` and drops the pair's slave; vt100's `Parser` is neither `Clone` nor `Debug`, so the runtime owns it and the model holds `Screen` snapshots; `/exit` and Enter typed together may be taken as a paste (a guard, not measured), hence the 400 ms #phase
- [gotcha] Running the tests inside a zaf phase needs the phase's `ZAF_*` variables unset: `app::actions::tests::plain_run_has_no_phase_env` reads them #testing
- [rule] No child inherits the chair's terminal: the saved stderr is `F_DUPFD_CLOEXEC`, and every `pre_exec` (the pty action, `b`'s detach) marks fds 3 and up close-on-exec (`process::close_above_stdio`: `close_range(CLOSE_RANGE_CLOEXEC)`, else an `fcntl` loop), never closing them, so std's exec-error pipe still works. Tests list `/proc/self/fd` in the child #safety
- [rule] Bracketed paste is on: a paste is one `Event::Paste`, its newline never Enter. It goes into the answer box (blank lines collapsed, made printable), or to Claude wrapped in `ESC[200~`/`ESC[201~` only when the session's screen asked for it (every control but tab and line ends dropped first, so no marker can form); anywhere else it is refused with a note #keys
- [rule] `printable` drops every character that draws nothing yet is text: all of Unicode 16.0's Cf (bidi, zero-width, soft hyphen, tag characters U+E0020-E007F) and the variation selectors; the pre-fill and typed keys pass through it too, so what is ruled is what was shown (S1) #safety
- [rule] R2: the answer box starts with only the first paragraph of Claude's proposal, cut near 400 characters (`detail::prefill`); it scrolls to the cursor with `↑/↓ N more lines` on its borders, opens maximised when it does not fit, and Enter is refused while any line is out of view (`AnswerView::hidden`) #answer
- [rule] R1: when the phase pane closes on its own (the action ended, not the Engineer leaving), every key and paste is ignored until 1 s (`QUIET_FOR`) passes with none, each dropped key starting it again (Q1), under "session ended", and keys typed to Claude while `Ending` are dropped, so typing never spills into `Sign it? [Y/n]` #phase
- [rule] R3: a fix is a typed verb (`FixVerb::{Doctor, ProfileInit}`, set by the hub on the problem, `serde(skip)`), never the fix's text parsed; it runs in the tab's root with every `ZAF_` but `ZAF_HOME` dropped, on a thread of its own, one at a time (`Chair::fixing`), killed (its process group) after 60 s, and is not waited for on quit #safety
- [rule] Only a panic on the chair's own thread hands the terminal back; another thread's goes to the log and to the status line (`terminal::deaths`). Writes run under `commit_guarded` (`catch_unwind`), and a write the dead writer cannot take is said as failed #safety
- [rule] A look reads a log only when it is a regular file inside the project's `.zaf/logs/` once canonicalized (opened `O_NONBLOCK|O_NOFOLLOW`, so no FIFO hangs it), and only its last 64 KiB for the tail #logs
- [rule] SIGTERM, SIGINT and SIGHUP close the chair as `q` does (a `sigaction` with `SA_RESETHAND` noting the signal, the loop breaking; a second signal ends zaf), exit code 128 and the signal; closing hangs a phase session up, kills it after 500 ms and waits up to 2 s for the phase thread. No `signal-hook` crate: it is only crossterm's dependency #safety
