# /teams:prepare-pr: one branch to an open PR, gate green

Takes one branch from "work done" to "PR open, gate green", then pauses for the merge. It never merges. Runs solo, or in `/teams:orchestrate`'s lifecycle at **Slice merge** (a slice or fix PR into the release's integration branch) and **Release end** (the release's one PR into main); there a `teams:machinery` Spawn runs it from the Orchestrator's checkout against the branch's workspace.

## Inputs

- **Arguments:** `[branch or workspace path] [title]`. Default: the current branch of the current checkout (jj: the bookmark on `@` or `@-`, from `jj bookmark list -r "@ | @-"`; none or several: ask). Given a workspace or a branch with a workspace: run every command there (`cd <workspace> && …`).
- **The teams file:** `.claude/TEAMS.md`, else `.claude/TEAMS.yaml`, else `.claude/TEAMS.toml`, at the root of the current checkout; if absent and this is a secondary workspace, at the root of the main checkout (git: the first path `git worktree list` prints; jj: `jj workspace root --name default`). It reads `Repository › owner, vcs, main, docs, gate, light gate, style`, `Branches › strategy, integration, slice, fix, engineer reviews, merge slice, merge main`, `Tracker › kind, project, commit format` and `Reviews › bot, security triggers`.
- **No teams file (solo):** detect. A `.jj/` folder means jj. The default branch from `gh repo view --json defaultBranchRef` (or `git symbolic-ref refs/remotes/origin/HEAD`). The gate from the CI config (`.github/workflows/*.yml` or the forge's equivalent). The title convention from recent commit subjects on the default branch. A ticket key from the branch name. Ask the Engineer once, in one round, only for what detection can't settle. A Spawn has no Engineer: it puts the question, with its pre-filled answer, in its report.
- **The base:** with `Branches › strategy` = `integration`, a branch matching `Branches › slice` or `fix` targets the integration branch with the same `{release}`, only when that branch exists on the remote (git: `git ls-remote --exit-code --heads origin refs/heads/<integration>` exits 0; exit 2 means absent; any other exit: stop, the remote wasn't reached; jj: after `jj git fetch --remote origin --branch <integration>`, `jj bookmark list --all-remotes <integration>` shows `<integration>@origin`), else `Repository › main`, unless `<docs>/releases/<release>/` exists (`<docs>` is `Repository › docs`; a relative path is from the main checkout named above): then the release is real and its integration branch isn't on the remote (never pushed, or already removed), so stop and say so. An integration branch, or any other branch, targets `Repository › main`. Solo: the default branch.

## Hard rules

- **Refuse on `Repository › main` or any `Branches › engineer reviews` branch** (solo: the default branch): say "branch first". Never push to them. **Never merge.**
- **Never rewrite a pushed branch.** A branch behind its base gets the base merged in (step 4), never rebased, so every push only adds commits and is plain: `git push -u origin <branch>`, which git refuses unless the remote tip is in what you push, and which auto mode lets through while still checking what it carries (it blocked leased pushes in testing, stalling the Spawn). Never `--force`; a lease only on the rebase path below. jj: `jj git push -b <bookmark>`; jj's own safety checks update the remote only if it still matches what jj last fetched (its built-in lease).
- **The rebase path.** When the project's own rules (its CLAUDE.md or contributing guide) want branches rebased, they win: step 4 rebases instead, and the push after it carries a lease keyed to the remote tip you fetched, `git push --force-with-lease=<branch>:<sha> -u origin <branch>` (`<sha>` from `git rev-parse origin/<branch>` after the fetch); jj pushes as above. Auto mode may block that leased push: a Spawn then reports the branch as rebased, gated and not pushed, for the Engineer to push. This is the pack's only rewrite of a pushed branch.
- **The remote-work check (git):** right after each fetch, when `origin/<branch>` exists, `git merge-base --is-ancestor origin/<branch> HEAD` must exit 0: this checkout has every commit the remote has (a merge keeps it so). Exit 1: the remote has commits this checkout lacks (`git log --oneline HEAD..origin/<branch>`), e.g. a committed review suggestion: stop and show them; integrate them with the Engineer (merging `origin/<branch>` in is one way); a Spawn reports them. Never push over them. Any other exit: stop. On the rebase path only, run it before rebasing, and exit 1 also passes when `git cherry HEAD origin/<branch>` prints no `+` line (every remote commit has an equivalent here, as after an earlier rebase); checked after a rebase instead, a conflict resolution changes that commit's patch, so `git cherry` would flag the branch's own commit. Passed, git's own check (a plain push) or the lease keyed to that fetch guards the push; a later re-fetch repeats the check. jj: a bookmark marked conflicted after the fetch (`jj bookmark list <bookmark>`), or a `jj bookmark move` refused as backwards or sideways, means the same: stop and show it; never `jj bookmark set` or `--allow-backwards` over it.
- **No interactive terminal:** no `git rebase -i`, `git add -i` or `-p`. Stage by pathspec.
- **Attribution:** commit messages end with the footer the session's attribution guidance gives; the PR body ends with the line it gives for PRs.
- **One PR per branch:** `gh pr list --head <branch> --state open --json number,url,baseRefName,isDraft`. One is open: update it, never open a second. Its base differs from the computed base: stop and ask; don't retarget silently.
- **Outward-facing:** before each push and before opening or editing the PR, say what you're about to do.

## Steps

1. **Survey.** git: `git branch --show-current`, `git status`, `git fetch origin`; on an integration branch (`Branches › integration`), which only changes through merged PRs, `git merge --ff-only origin/<branch>` (refused: stop and say so); then the remote-work check (hard rules), `git log --oneline origin/<base>..HEAD`, `git diff --stat origin/<base>...HEAD`. jj: `jj status`, `jj git fetch --remote origin --branch <bookmark> --branch <base>` (only this branch and its base: a full fetch rewrites other workspaces; `/teams:cleanup` owns it), then the remote-work check, `jj log -r "<base>@origin..<bookmark>"`, `jj diff --from <base>@origin --to <bookmark> --stat`. Find the ticket in the branch name (`Tracker › project` key and number, e.g. `abc-12-…` gives `ABC-12`; `github`: the issue number), and its title from the tracker's tools when present (GitHub: `gh issue view <n> --json title,url`). A step with nothing to do (no changes, not behind) passes on.

2. **Format-write.** Run the writing form of the gate's format check (the check is in `Repository › gate` or CI; its writing form drops the check flag, e.g. a `--check` becomes a write). It may edit files; they're committed next. **On an integration branch** (only changes through merged PRs), an edit here or any uncommitted change means stop and say so; nothing is committed on it.

3. **Commits.** Keep existing clean commits (lifecycle programmers already committed). Commit only new or formatted changes, granular by pathspec, one coherent story each, titled per `Tracker › commit format`, else the repo's convention. git: `git add <paths>` then `git commit -m "<title>" -m "<footer>"`. jj: `jj commit <paths> -m "<title>" -m "<footer>"`, then `jj bookmark move <bookmark> --to @-` if the bookmark didn't follow.

4. **Merge the base in if behind.** git: `git log --oneline HEAD..origin/<base>` non-empty, then `git merge --no-edit origin/<base>`. jj: `jj log -r "<bookmark>..<base>@origin"` non-empty, then `jj new <bookmark> <base>@origin -m "Merge <base> into <bookmark>"` (the merge change becomes `@`); with no conflicts, `jj bookmark move <bookmark> --to @`, then `jj new`, so later edits land on top. **On conflict, stop:** git pauses the merge (`git diff --name-only --diff-filter=U` lists the files); jj records them in the merge change (`jj log -r "conflicts() & @"`). Show them and resolve with the Engineer, never by guessing; then `git commit --no-edit` (jj: resolve in `@`, then move the bookmark as above). A Spawn undoes the merge and reports the conflicts: git `git merge --abort`; jj `jj new <bookmark>`, then `jj abandon <the merge change's id>`. On the rebase path (hard rules): git `git rebase origin/<base>`, jj `jj rebase -b <bookmark> -o <base>@origin`, with the same stop on conflict (git: `git rebase --continue` after resolving; a Spawn runs `git rebase --abort` first). **An integration branch** (`Branches › integration`) is neither rebased nor merged into here: behind its base, stop and say so; in the lifecycle a `teams:machinery` Spawn merges main into it.

5. **The gate.** Run `Repository › gate` exactly (its `light gate` never stands in here), judged on exit code **and** output. Solo: every step the CI config runs, from the directory CI runs it in, with CI's environment variables set and without services CI lacks (a reachable local database or container can hide a failure CI hits). **Never push red.** A step needing a service that isn't reachable: say so and ask (CI will still run it); a Spawn reports it. Then the rest of the definition of done (the project's `CLAUDE.md`, else `/teams:orchestrate`'s **Definition of done**), before the PR:
   - **Docs** on changed signatures, per `Repository › style` (`/teams:document`).
   - **The review loop closed.** In the lifecycle: a slice or fix PR has its build lead's critique settled and, when triggered, its security review passed; the release PR has the last milestone's QA and the release reviews passed. Every finding applied or listed as deferred. Solo: offer `/teams:critique`.
   - **Security review** when the diff touches a `Reviews › security triggers` item (solo: the template's list: authentication; authorization and permissions; sessions, tokens, secrets and keys; cryptography; untrusted input; trust boundaries; network egress; personal data storage). In the lifecycle, a slice or fix PR's security reviewer (**Slice merge**) covered it, and a release PR's release reviews include security: check that its report passed (missing: stop and say so). Solo: run it in a `teams:designer` Spawn with `model: "opus"` on the Agent call, even when this session runs on Sonnet; the review is the project's own, or Claude Code's `/security-review` when present.
   A red here blocks like a red gate.

6. **Push**, plainly (leased only on the rebase path), only after the remote-work check passed on the fetch the push relies on. Already-open PR: say whether this push carries a fix.

7. **Open the PR** with `gh pr create --base <base> --head <branch> --title "<title>" --body-file <file>`, the body file outside the repo (the session's scratch or temp folder). Updating an open PR: `gh pr edit <n> --body-file <file>` when the body no longer fits.
   - **Title:** the argument, else per `Tracker › commit format`, else the repo's convention.
   - **Body:** what it does in plain words; implementation choices; deferred findings; links to reviews; how to check it locally; the ticket link, or a closing keyword when the tracker reads one (GitHub: `Closes #<n>`); the attribution line last. A release PR (an integration branch into main) also carries a table of its milestones, each with its range (from milestones.md) and links to its architect and QA reports, and each release review's must-fixes with how they closed, when `Repository › owner` = engineer; with `others`, that table goes in `<docs>/queue.md`, since the reports aren't in git. Run by a Spawn: the body's substance comes from its brief; never invent it, and report what the brief lacks.
   - **Review bot:** request `Reviews › bot` (solo: none unless the Engineer names one) only on a PR into an engineer-reviews branch with real review surface. Request it for logic, a security-trigger item (a spec that defines a security boundary counts), or non-trivial size (several files of logic, roughly 50 changed code lines, real branching or error handling). Skip it for docs-only, config-only or mechanical changes (renames, dependency bumps); skipping is the waiver: write `Review bot: not requested (<reason>)` in the PR body. Unsure: request. `gh pr edit <n> --add-reviewer <login>` (some bots take a special value: `gh pr edit --help` lists them); fallback `gh api --method POST "repos/{owner}/{repo}/pulls/<n>/requested_reviewers" -f "reviewers[]=<login>"`. Confirm with `gh pr view <n> --json reviewRequests`. Say whether you requested it and why.

8. **Pause.** Print the PR URL. Name the merge method that fits: `Branches › merge main` for a base in `engineer reviews`, else `Branches › merge slice`. Solo: what the repo allows (`gh repo view --json mergeCommitAllowed,squashMergeAllowed,rebaseMergeAllowed`), recommending one by how the base's history reads (one commit per PR: squash, which also keeps a branch's catch-up merges off a linear base). **Don't merge.** Wait for word that it's merged. A Spawn puts the PR URL and merge method in its report and ends; the word goes later to whoever runs the lifecycle's **Clean up** step.

9. **After the merge** (on the Engineer's or the Orchestrator's word): `/teams:cleanup <branch>` removes the workspace and branch. Solo, when the branch is checked out in the Engineer's own checkout, offer, and only with their yes: git `git switch <base>`, `git pull --ff-only`, `git branch -d <branch>` (a squash merge makes `-d` refuse; with the PR shown merged, `-D`), `git fetch --prune`. jj: `jj git fetch --remote origin --branch <base>`, `jj new <base>@origin`, `jj bookmark forget <branch>` if it's still listed.

## Notes

- **gh absent or failing:** say in one line what wasn't checked (an open PR, CI state, the reviewer request); never invent PR or CI state. Another forge: its CLI's equivalent of each `gh` command.
- **Workspaces:** with `cd <workspace> && …` on every command, this runs from any checkout without switching the Engineer's.
