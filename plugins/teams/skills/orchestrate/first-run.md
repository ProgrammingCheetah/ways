# First run: creating the teams file

Read once per project, when no `.claude/TEAMS.*` exists. Everything here is asked in one round, with every answer pre-filled. Nothing is written until the Engineer answers.

1. **Read** the CLAUDE.md files, CONTRIBUTING, CI config and any design docs. Find where decisions are recorded.
2. **Offer to create the teams file,** and ask, in one round:
   - **Its format:** Markdown (recommended, `teams-file.md`), YAML or TOML (`teams-file.toml`; YAML uses the same keys).
   - **Whether the repo is the Engineer's own.** It is when there is no remote, or the remote's owner is, ignoring case, the signed-in host account or one of the orgs in the environment variable `WAYS_OWN_ORGS`. The remote is the push remote: `origin`, or the remote `git push` uses. Its owner is the `<owner>` in `https://<host>/<owner>/<repo>` or `git@<host>:<owner>/<repo>`; on GitLab with subgroups, the top-level group. The signed-in account: `gh api user --jq .login`, on a host other than github.com `gh api user --hostname <host> --jq .login`, if `gh` is present. `WAYS_OWN_ORGS` is comma-separated, spaces around the commas ignored; read it with `printenv WAYS_OWN_ORGS`, in PowerShell `$env:WAYS_OWN_ORGS`; unset or empty lists none. A fork is never own by its owner, even the Engineer's login. It is a fork when `gh api repos/<owner>/<repo> --jq .fork` prints `true` (add `--hostname <host>` off github.com); then run the test on its parent's owner instead (`--jq .parent.owner.login`), and when the parent is a fork too (`--jq .parent.fork`), on the original's (`--jq .source.owner.login`, GitHub's root of the fork network). Can't tell whether it's a fork (no `gh`, another forge without its CLI's equivalent, an error): not own. Never by permission: admin rights on a repo, as on a team's shared repos on a work computer, don't make it the Engineer's. The answer pre-fills `Repository › owner`; unsure means `others`. The nodes question and steps 3 and 5 use this answer; they don't test it again.
   - **Every setting,** detected where possible: VCS and workspaces folder, the gate (exactly what CI runs) and a light gate, branch strategy (`integration`; `trunk` only where the repo's own rules want a PR per change into main), whether CI runs on PRs into the integration and fix patterns (if not, the worksheet says so) and the merge methods the repo allows, tracker, docs folder, lanes, limits, release documents and format, and security and compliance triggers fitted to this project (the template's are generic).
   - **The teams:** missions, owned paths and a named lead each (programmers are short-lived, named per task), the top-level QA's name (the qa row), and the review teams' reviewers (the architects' lead is the architect), always including the internal team, the security team and the release reviewers unless the Engineer opts out.
   - **nodes:** pre-selected yes in the Engineer's own repo (`Repository › owner` = engineer); no in anyone else's, since the first chart is costly and there its settings and refs would stay local-only, in one checkout.
   - **Main's protection on the server,** checked first. Say plainly that it is the real guard; permission rules are only a speed bump (step 6). Confirmed only when the server refuses a direct push, a force push and a deletion of `Repository › main` from the account the agents push as (the Engineer's own). GitHub: `gh api repos/{owner}/{repo}/rules/branches/<main>` lists active `pull_request`, `non_fast_forward` and `deletion` rules, and each one's ruleset (`gh api repos/{owner}/{repo}/rulesets/<ruleset_id>`) answers `current_user_can_bypass` = `never`; or classic protection (`gh api repos/{owner}/{repo}/branches/<main>/protection`) has `required_pull_request_reviews`, `enforce_admins` on (classic protection exempts admins by default), and `allow_force_pushes` and `allow_deletions` off. Anything less, or no answer: unconfirmed. Unconfirmed: recommend turning it on, pre-selected yes: every change to main through a pull request, force pushes and deletion blocked, no bypass. In someone else's repo it's a request to its owners (step 6). Never change it yourself. Protection stops pushes, not merges: with no required approval, any agent signed in to `gh` as the Engineer can still `gh pr merge` a PR into main; there only the rule that a PR into an `engineer reviews` branch is the Engineer's to merge stands.
3. **Exclude first.** Your first write is the repo's exclude file, before any other file, with no jj command in between (jj snapshots, and so tracks, any file not yet excluded). Find it with `git rev-parse --git-path info/exclude` (git, and jj colocated with git). In jj without colocation it is `info/exclude` in the git directory that `.jj/repo/store/git_target` names (an absolute path, or relative to `.jj/repo/store/`; if `.jj/repo` is a file, it names the repo directory to read instead). Add, each only if missing and not already ignored (`git check-ignore -q <path>` succeeds):
   - in every repo: `.claude/settings.local.json`;
   - in a repo that isn't the Engineer's (`Repository › owner` = others), also: the teams file, `CLAUDE.local.md` and the docs folder.
   Can't find the exclude file: say so, and write nothing else until the Engineer decides.
4. **Write `.claude/TEAMS.<format>`** with your file tools. Opt-outs go in its **Opt-outs** with the date and the Engineer's words. Never regenerate it over the Engineer's edits.
5. **Write the pointer,** this one line, unchanged, into `CLAUDE.md` (the Engineer's own repo, `Repository › owner` = engineer) or `CLAUDE.local.md` (anyone else's):
   ```
   **Way of working: teams.** The main session is the Orchestrator: it loads the `teams:orchestrate` skill at the start of each session and again after compaction, and follows it. A Spawn (any subagent) skips this line and follows its brief.
   ```
   If the repo has an `AGENTS.md` and neither a `CLAUDE.md` nor a `CLAUDE.local.md` existed before, put `@AGENTS.md` on the line after the pointer: the new file would otherwise stop Claude reading the `AGENTS.md`.
6. **Hand the Engineer the settings worksheet.** Never edit settings yourself, local or on the server. Read `.claude/settings.local.json` if it exists, then give the full file content to save, keeping every existing key and adding (as `PowerShell(…)` rules on a machine whose shell is PowerShell):
   - `permissions.additionalDirectories`: the workspaces folder, as an absolute path;
   - `permissions.allow`: the gate and light gate (e.g. `Bash(npm test *)`), the VCS commands the lifecycle runs (e.g. `Bash(git worktree *)`, `Bash(git status *)`, `Bash(git diff *)`, `Bash(git commit *)`, `Bash(git fetch *)`, `Bash(gh pr list *)`, `Bash(gh pr view *)`), and no push rule at all. Every lifecycle push is plain, since a branch behind its base gets the base merged in rather than rebased, and auto mode lets plain pushes through unprompted while still checking what they carry. Tested on Claude Code 2.1.302 with no push rule: auto mode let `cd <workspace> && git push` after a catch-up merge and `jj git push -b` through, and blocked leased pushes as `[Git Destructive]`; an allow rule doesn't settle a `cd … &&` command, which every Spawn runs. Never add a push allow rule (`Bash(git push *)`, `Bash(jj git push *)`, `Bash(git push --force-with-lease=*)`): an allow rule resolves before auto mode's classifier, which then never checks what the push carries (secrets, sensitive files, private material bound for a public repo); the forge's secret scanning is the server-side counterpart. A project whose own rules want rebased branches keeps them: its leased pushes may stall in auto mode, and the Engineer pushes those;
   - `permissions.deny`, for `Repository › main` and each `Branches › engineer reviews` branch `<b>`, by name (never a literal `main`): `Bash(git push * <b>)`, `Bash(git push * <b> *)`, `Bash(git push * +<b>)`, `Bash(git push * +<b> *)`, `Bash(git push *:<b>)`, `Bash(git push *:<b> *)`, `Bash(git push *refs/heads/<b>)`, `Bash(git push *refs/heads/<b> *)` (the full ref plain, as `+refs/heads/<b>` and as `<src>:refs/heads/<b>`, but not `refs/heads/<b>-x`); and once: `Bash(git push *--all*)`, `Bash(git push *--branches*)`, `Bash(git push *--mirror*)`. With jj, also per branch `Bash(jj git push * <b>)`, `Bash(jj git push * <b> *)`, `Bash(jj git push *=<b>)`, `Bash(jj git push *=<b> *)`, and once `Bash(jj git push *--all)`, `Bash(jj git push *--all *)` (not `*--all*`: that also matches jj's `--allow-private`, `--allow-empty-description` and `--allow-conflicts`), `Bash(jj git push *--tracked)` and `Bash(jj git push *--tracked *)` (`--tracked` pushes every tracked bookmark, main included once it moved locally; the lifecycle never uses it, it pushes with `-b`). Never a `*<b>*` pattern: it would also match a slice branch such as `api/v0.2-1-domain`. Deny beats allow, in every mode.

   Say in the worksheet, above step 1: these rules match the command, not the folder, so they also let any agent run those commands in the Engineer's own checkout without asking. Say plainly too: the deny rules are a speed bump, not a guard. They match the command as written, so `git -C <path> push`, a bare `git push` while on main, a bare `jj git push` (it takes main along once main moved locally), or a branch named by pattern gets past them; what keeps agents off main is the server's protection of it (step 2). Say also: unattended Spawns need auto mode, where the organisation allows it. Every Spawn command starts `cd <workspace> &&`, and in Manual mode a `cd` into another directory followed by `git` asks for approval whatever the allow rules say, since git can run that directory's hooks (tested: a matching `Bash(git fetch *)` didn't spare it). In auto mode the classifier decides those commands instead (a matching allow rule didn't settle a `cd … && git push` either). Never rewrite briefs to `git -C <path>` to avoid the prompts: the deny rules don't match that form, so it would drop the speed bump too. The steps: open the file in an editor; replace its content with the block you give; save; restart Claude in the project. Done when: `/permissions` lists the folder and the rules.

   With `Repository › owner` = others, the worksheet never gives a command or click path that changes the repo's protection, even when the Engineer is an admin there: its step says to ask the repo's owners for it (every change to main through a pull request, force pushes and deletion blocked, no bypass); done when step 2's check confirms it or the owners decline. Otherwise, when the Engineer chose to turn on main's protection, the next worksheet steps do it with the exact command or click path; done when step 2's check confirms it. On GitHub, the command: save this one line as `main-protection.json` outside the repo, with `<main>` filled in:
   ```
   {"name":"Main protection","target":"branch","enforcement":"active","bypass_actors":[],"conditions":{"ref_name":{"include":["refs/heads/<main>"],"exclude":[]}},"rules":[{"type":"deletion"},{"type":"non_fast_forward"},{"type":"pull_request","parameters":{"required_approving_review_count":0,"dismiss_stale_reviews_on_push":false,"require_code_owner_review":false,"require_last_push_approval":false,"required_review_thread_resolution":false}}]}
   ```
   then run `gh api --method POST repos/{owner}/{repo}/rulesets --input main-protection.json`. Or the click path: Settings › Rulesets › New ruleset › New branch ruleset; Ruleset name `Main protection`; Enforcement status Active; Bypass list empty; Target branches › Add a target › the default branch; Restrict deletions, Require a pull request before merging, Block force pushes; Create.

   When protection stays off (the Engineer declines, or a repo's owners do), record it in **Opt-outs** with the date and the Engineer's words, and say in the worksheet that only the deny speed bump stands.
7. **nodes, when chosen:** if `nodes --version` doesn't answer 0.7.0 or later, or the `nodes` plugin's skills (e.g. `/nodes:chart`) are absent, hand a worksheet: `claude plugin install nodes@ways`, then the binary, either from https://github.com/ZurNetwork/nodes/releases (Linux and macOS builds) or `cargo install --git https://github.com/ZurNetwork/nodes --locked --tag <the latest tag, which you look up and write in>`. On Windows only the `cargo` route exists. If the Engineer declines, record the opt-out.
8. **Ask for the first release's scope,** or the off-cycle work, and run the lifecycle.
